# 리뷰 — 저장 구조와 대표 리뷰 선정

리뷰를 어디에 어떻게 저장하고, 화면에 보여줄 대표 리뷰를 어떤 기준으로 뽑는지 확정한 문서입니다.
모든 수치는 Steam API 실측 기준입니다. 측정일 2026-09-05.

---

## 저장 구조 — 전량은 파일, 화면에 쓸 것만 DB

리뷰는 두 곳에 저장합니다. 나누는 것이 아니라 **전량을 파일에 두고 일부를 DB에 복사**합니다.

```
HDFS (Parquet)        리뷰 전량 1.5억 건
       │
       │ 배치가 읽어서 집계
       ↓
PostgreSQL            집계 결과
                      + 최신 패치의 패치 후 7일 리뷰 (약 54만 건)
       │
       │ 화면이 조회
       ↓
     사용자
```

### 규모 실측

전체 카탈로그 184,389개 게임을 조사한 결과입니다.

| 항목 | 값 |
| --- | --- |
| 전체 리뷰 | 약 1.5억 건 |
| Parquet 압축 후 (Snappy) | 약 29GB |
| MySQL InnoDB 로 넣었을 경우 | 55.8GB + 인덱스 |
| 파티션 키 | appid |

리뷰 1건당 실측 크기입니다.

| 압축 | 행당 | 1.5억 건 환산 |
| --- | --- | --- |
| 없음 | 235.2 B | 35.3 GB |
| Snappy (Spark 기본) | 146.5 B | 22.0 GB |
| ZSTD | 106.4 B | 16.0 GB |
| GZIP | 96.4 B | 14.5 GB |

### 게임 4.5% 가 리뷰 94.5% 를 갖고 있습니다

| 리뷰 수 | 게임 수 | 누적 리뷰 |
| --- | --- | --- |
| 100,000 이상 | 228 | 76.4M |
| 10,000 이상 | 1,757 | 120.6M |
| 1,000 이상 | 8,239 | 140.4M |
| 100 이상 | 27,832 | 146.7M |

중앙값이 4건이고 36% 는 리뷰가 아예 없습니다. **대부분의 게임은 저장할 리뷰가 거의 없습니다.**

### 왜 나누지 않고 복사하는가

집계는 항상 HDFS 전량을 읽습니다. 화면용 리뷰만 빼서 DB 로 옮기면 그 리뷰들이 집계에서 빠져 숫자가 틀어집니다.

```
잘못된 방식   HDFS 1.4946억(화면용 제외) + DB 54만
             → 집계할 때 두 곳을 합쳐야 함

맞는 방식     HDFS 1.5억 (전량)
             DB 는 그중 54만 건을 복사해 보관
             → 집계는 HDFS 만, DB 는 조회 전용
```

중복 비용은 작습니다. DB 적재분은 **전체의 0.36%**, 용량으로는 329MB 입니다.

### 각 저장소의 역할

| 저장소 | 역할 |
| --- | --- |
| HDFS | 원본 보관 + 배치 입력. 매일 전량 재집계 시 여기를 읽음. 화면은 접근 안 함 |
| PostgreSQL | 화면 조회 전용. 집계 결과 + 최신 패치 창 리뷰 54만 건. 응답 10~50ms |

## 수집 운영 — 매일 전량 재수집

증분 수집이 아니라 **매일 전량을 다시 받습니다.** 유저 반응 신호를 하나도 놓치지 않기 위해서입니다.

### 증분으로는 놓치는 것이 생깁니다

`filter=recent` 는 **작성일 순** 정렬입니다. 실측으로 확인했습니다.

```
created  기준 정렬 위반   0건
updated  기준 정렬 위반   6~14건
```

작성일 순이므로 **오래전에 작성됐다가 최근에 수정된 리뷰는 앞으로 올라오지 않습니다.** 증분으로 긁으면 이런 리뷰를 놓칩니다.

리뷰 9만 건 중 수정된 4,067건의 수정 간격입니다.

| 작성 후 | 누적 비율 |
| --- | --- |
| 당일 | 58.2% |
| 7일 이내 | 77.0% |
| 30일 이내 | 91.9% |
| 90일 이내 | 98.3% |
| 최대 | 210일 |

게임마다 편차가 큽니다. CS2 는 최대 3일인데 Dead Cells 는 210일입니다.

**삭제는 증분으로 아예 감지할 수 없습니다.** API 응답에서 사라지는 것을 알려면 전량을 받아 비교하는 수밖에 없습니다.

### 소요 시간

```
전량 수집   약 5.7시간
            임계경로 = CS2 러시아어 27,032 페이지
            동시성 64 · 버스트 2,624 리뷰/초 기준
```

### 날짜별 디렉터리에 쓰고 링크를 교체합니다

배치가 중간에 실패해도 이전 데이터가 살아있어야 합니다.

```
/review_raw/dt=2026-09-05/     오늘 수집분
/review_raw/dt=2026-09-04/     어제 (성공 확인 후 삭제)
/review_raw/current            심볼릭 링크
```

수집이 완전히 끝난 뒤에만 `current` 를 교체합니다. 실패하면 링크가 어제를 가리킨 채로 남아 서비스가 계속 동작합니다.

보관은 **최근 2일치**면 충분합니다. 22GB × 2 = 44GB 입니다.

### 전량 재수집해도 GPU 부담은 늘지 않습니다

```
수집    전량 1.5억 건을 새로 받음
분류    기존 review_topic 과 review_id 로 조인
        → 텍스트가 바뀐 것만 재분류
        → 신규 + 수정분 = 하루 수십만 건 → 수 분
```

**리뷰 내용이 같으면 토픽도 같습니다.** 다시 임베딩할 이유가 없습니다.

`review_topic` 은 날짜 디렉터리를 두지 않고 누적으로 유지합니다. 삭제된 리뷰의 토픽이 남아 있어도 원본 기준 조인이라 자동으로 빠집니다.

### 하루 파이프라인

```
00:00   전량 재수집 시작              API → HDFS /review_raw/dt=오늘
05:42   수집 완료 · current 링크 교체
05:45   변경분만 토픽 분류 (GPU)       → /review_topic
06:00   Spark 전량 재집계             HDFS 22GB 스캔
??:??   PostgreSQL 적재
```

집계를 매일 전량 다시 하는 이유는 **수정일 기준 집계라 과거 숫자가 계속 바뀌기 때문**입니다. 증분 집계가 불가능합니다.

### 아직 검증되지 않은 두 가지

**① 지속 수집이 가능한가**

측정된 것은 짧은 버스트(동시성 64에서 429 없음, 2,624 리뷰/초)뿐입니다. **5.7시간 연속 호출을 스팀이 허용하는지는 확인하지 않았습니다.** 몇 시간 돌리다 차단되면 배치가 통째로 실패합니다.

하루 잡아서 전량을 한 번 돌려보는 것이 이 설계의 유일한 미검증 지점입니다.

**② Spark 집계가 몇 시간인가**

워커 대수에 따라 갈립니다. 1 / 2 / 4대로 재보면 스케일아웃 효율도 함께 나오고, 그 숫자는 분산처리 설계의 근거로 쓸 수 있습니다.

두 숫자가 나오면 "00시 시작 → 몇 시 완료" 가 확정되고, 화면에 표시할 갱신 시각도 정해집니다.

## 토픽 분류 — 임베딩 방식

리뷰를 불만·만족 요소 5종으로 분류합니다.

| key | 이름 |
| --- | --- |
| balance | 밸런스 / 너프 · 버프 |
| bug | 최적화 / 버그 / 크래시 |
| ui | 시스템 / UI · 편의성 |
| ops | 외부 / 운영 이슈 |
| bm | 과금 / 재화 (BM) |

### 키워드 사전이 아니라 임베딩을 쓰는 이유

키워드 매칭은 같은 단어의 다른 뜻을 구분하지 못합니다. 실측에서 이런 오탐이 나왔습니다.

```
'FPS게임의 전설답네요.'          fps = 프레임 아니고 장르     ✗ 오탐
'순정 FPS 당장 조인'                                        ✗ 오탐
'NO.1 FPS GAME IN MY LIFE'                                 ✗ 오탐
'纯粹的fps'                                                 ✗ 오탐

'아 진짜 렉'                     진짜 성능 불만               ✓
'그만팅겨스렉이게임'                                          ✓
```

짧은 리뷰 59건 중 키워드가 걸린 것을 열어보니 **진짜 불만은 2~3건**이었습니다. `fps` 하나가 "프레임"과 "1인칭 슈터" 두 뜻으로 쓰이는데 키워드 매칭은 문맥을 못 봅니다.

**다국어 처리도 임베딩이 유리합니다.** 언어마다 키워드 사전을 따로 만들 필요가 없습니다.

### 방식 — centroid 코사인 유사도

```
① 토픽마다 대표 리뷰 30~50건을 손으로 고름
② 임베딩해서 평균  →  centroid 5개
③ 각 리뷰를 임베딩  →  centroid 와 코사인 유사도
④ 임계값을 넘는 토픽을 전부 할당 (다중 라벨)
```

다국어 모델을 쓰면 **한국어 예시로 만든 centroid 가 영어 · 중국어 리뷰에도 통합니다.** 언어별로 centroid 를 따로 만들 필요가 없습니다.

`topic_keyword` 사전은 폐기하지 않고 **검증기로 남깁니다.** 명백한 모순(예: 성능 키워드가 가득한데 balance 로만 분류)을 걸러내는 용도입니다.

### 대상 — 30바이트 초과 리뷰만

```
전체 리뷰            1.5억 건
30바이트 초과        약 8,250만 건 (55%)
```

리뷰 중앙값이 34바이트입니다. `great`, `nice`, `good game` 같은 것은 분류할 내용이 없어 임베딩 대상에서 제외합니다. **대표 리뷰 선정 필터와 같은 기준이라 통일됩니다.**

### 벡터는 저장하지 않습니다

```
리뷰 텍스트  →  임베딩 (메모리)
             →  centroid 와 코사인 유사도
             →  토픽 할당
             →  결과만 저장. 벡터는 버림
```

전체를 저장하면 768차원 기준 600GB 가 됩니다. **분류에만 쓰면 저장할 이유가 없습니다.**

```
/review_topic/appid=730/part-0000.parquet
   review_id · topics
   234499291 · ['balance', 'bm']
   234494067 · ['bug']
   234491102 · []                 ← 미분류
```

### 소요 시간 — RTX 4070 기준

| 모델 | 파라미터 | 차원 | 초당 | 8,250만 건 |
| --- | --- | --- | --- | --- |
| multilingual-e5-small | 118M | 384 | ~5,000 | 약 4.6시간 |
| multilingual-e5-base | 278M | 768 | ~2,000 | 약 11.5시간 |
| bge-m3 | 568M | 1024 | ~1,000 | 약 23시간 |

**e5-small 로 시작합니다.** 5개 토픽 분류는 미세한 판단이 아니라 작은 모델로 충분합니다. 품질이 부족하면 base 로 올립니다.

위 수치는 추정입니다. 리뷰 1만 건으로 실측하면 정확한 값이 나옵니다.

```python
model = SentenceTransformer("intfloat/multilingual-e5-small", device="cuda")
t0 = time.time()
vecs = model.encode(texts, batch_size=256, normalize_embeddings=True)
print(f"{len(texts)/(time.time()-t0):.0f} 건/초")
```

### VRAM 제약

RTX 4070 은 12GB 입니다.

```
multilingual-e5-small (fp16)     0.24 GB    여유
Qwen2.5-7B (fp16)               14 GB      들어가지 않음
Qwen2.5-7B (4bit)               ~4.5 GB    가능
```

**임베딩 배치와 AI 요약 배치를 동시에 돌릴 수 없습니다.** 순차로 실행합니다. 그리고 시연 중에 배치가 돌면 VRAM 부족으로 요약이 실패하니 야간에 돌립니다.

### 분류 결과의 실측 특성

```
분류 커버리지    42.1%   (나머지는 5개 토픽에 안 걸림)
평균 매칭 수     1.8개   (다중 라벨)
```

42.1% 는 낮아 보이지만 신호는 분명합니다.

```
실제 패치      토픽 구성 10~28%p 이동
단순 공지      토픽 구성  2~5%p 이동
```

미분류 리뷰는 짧고 추천 수가 적은 쪽에 몰려 있어 **분류 결과에 편향을 만들지 않습니다.**

## 통계 범위와 대표 리뷰 범위는 다릅니다

목적이 다르므로 창을 다르게 잡습니다. 이 구분이 섞이면 안 됩니다.

| 구분 | 무엇 | 창 |
| --- | --- | --- |
| 통계 | 긍정률 · 토픽 구성의 before / after | 패치 전 7일 / 패치 후 7일 각각 |
| 밴드 경계 | 플레이타임 4분위 기준선 | 패치 전후 14일 (전후 통합) |
| 대표 리뷰 | 화면에 보여줄 리뷰 5건 | 패치 후 7일 |

```
통계        "패치 전 74.1% → 후 38.2%"      비교하려면 전후 둘 다 필요
밴드 경계    전후를 같은 기준으로 나눠야 비교 가능
대표 리뷰    "패치 후에 사람들이 이렇게 말했다"   후만 있으면 됨
```

목업의 창 구조입니다.

```
date: '2026-04-09'  ·  range: '04/02 – 04/14'  ·  patchIdx: 7

04/02 ~ 04/08   패치 전 7일
04/09           패치일
04/10 ~ 04/14   패치 후
```

`PT_BANDS`, `LANGS`, `TOPICS` 모두 before / after 값을 가집니다. 대표 리뷰만 패치 후에서 뽑습니다.

## 공통 규칙 (대표 리뷰)

| 항목 | 값 |
| --- | --- |
| 창 | 패치 후 7일 |
| 후보 필터 | 리뷰 길이 30바이트 초과 |
| 정렬 | votes_up 내림차순, 동점 시 길이 내림차순 |
| 선정 건수 | 5건 |
| 임계값 | 없음 (순위만 매김) |
| AI 요약 입력 | 선정된 5건 |
| 긍정/부정 | voted_up 을 배지로 표시. 따로 뽑지 않음 |

**임계값을 두지 않는 이유**

목업 초안에는 `helpful ≥ 20` 이라는 기준이 있었으나 실측 결과 성립하지 않습니다.

```
패치 후 7일 창에서 helpful >= 20 인 리뷰 개수
  CS2 0건 · Terraria 0건 · Slay the Spire 0건 · Hades 0건 · Dead Cells 0건
  STS2 1건 · HELLDIVERS 2 1건 · Valheim 2건
```

12개 게임 중 5개에서 대표 리뷰가 아예 나오지 않습니다. 도움됨 투표는 쌓이는 데 시간이 걸려 7일 안에 20표를 받는 경우가 극히 드뭅니다.

```
전체 리뷰 4.8만 건 기준 votes_up 분포
  1표 이상 15.3% · 5표 이상 2.7% · 10표 이상 1.3% · 20표 이상 0.5%
```

임계값을 없애고 정렬만 하면 상위 5건은 항상 확보됩니다.

**길이 30바이트 필터를 두는 이유**

리뷰 중앙값이 34바이트입니다. 절반가량이 아래 수준이라 요약할 내용이 없습니다.

```
'great'  'Nice'  'peak'  'good game'  'rrsdafda2erfew'  '♥♥♥♥♥ game'
```

**정렬만으로도 대부분 걸러지지만 완전하지는 않습니다.** 길이 필터 없이 좋아요 순 상위 5건을 뽑아본 결과, 30~100바이트 미만 리뷰가 상위에 드는 경우가 60건 중 9건(15.0%)이었습니다.

```
HELLDIVERS 2   26표  23B  긍  'Say hello to DEMOCRACY!'
```

최다 득표가 23바이트 밈 리뷰인 경우가 있습니다. 공감 자체는 진짜지만 AI 요약 입력으로는 뽑을 정보가 없습니다.

**100바이트가 아니라 30바이트인 이유**

100바이트로 자르면 내용 있는 짧은 리뷰까지 걸립니다.

```
Dead Cells   3표  95B  긍  'Suena a todas horas en mi cabeza la música de la Ce...'
```

30바이트는 빈 리뷰만 제외하고 실제 감상은 살립니다. 임베딩 분류 대상 필터와도 기준이 같아 통일됩니다.

**나중에 넣는 것보다 지금 넣는 편이 쌉니다.** 필터를 나중에 추가하면 대표 리뷰가 바뀌고, 이미 만들어둔 AI 요약을 전부 다시 생성해야 합니다.

## ② 플레이타임 구간별

| 항목 | 값 |
| --- | --- |
| 밴드 경계 계산 | 패치 전후 14일 리뷰의 플레이타임 4분위 |
| 통계 (긍정률·토픽) | 패치 전 7일 / 후 7일 각각 → before / after |
| 대표 리뷰 창 | 패치 후 7일 |
| 단위 | 게임 × 최신 패치 × 밴드 4개 |
| 밴드 | 4구간 (Q1 ~ Q4) |
| 선정 | 밴드별 좋아요 순 5건 |
| AI 요약 | 밴드마다 1개 (패치당 4개) |

밴드 경계는 전후 14일로 계산합니다. 전후를 같은 기준선으로 나눠야 before / after 비교가 성립하기 때문입니다. 대표 리뷰만 그 경계를 써서 패치 후 7일 리뷰에서 뽑습니다.

### 밴드 경계 계산 — 패치 창 기준

**패치 전후 7일에 달린 리뷰들의 playtime_at_review 를 4분위로 나눕니다.**

```
Q1  하위 25%
Q2  25% ~ 중앙값
Q3  중앙값 ~ 75%
Q4  상위 25%
```

경계는 패치마다 다시 계산합니다. 게임 전체 누적 리뷰가 아니라 그 패치 창의 리뷰만 씁니다.

**표본이 항상 균등하게 확보됩니다**

분위수로 나누므로 정의상 정확히 4등분됩니다.

| 게임 | 패치 | 창 리뷰 | 밴드별 건수 |
| --- | --- | --- | --- |
| HELLDIVERS 2 | 08-25 | 4,546 | 1136 / 1137 / 1136 / 1137 |
| STS2 | 08-15 | 2,751 | 687 / 688 / 688 / 688 |
| Valheim | 08-20 | 1,053 | 262 / 262 / 262 / 263 |
| Slay the Spire | 08-15 | 552 | 138 / 138 / 138 / 138 |
| Dead Cells | 06-08 | 344 | 86 / 86 / 86 / 86 |

창 리뷰가 120건만 있으면 각 밴드 30건이 자동 보장됩니다.

**경계는 패치마다 흔들립니다**

| 게임 | 패치 수 | 중앙값 범위 | 흔들림 |
| --- | --- | --- | --- |
| STS2 | 3건 | 84.4 ~ 88.8h | 1.1배 |
| Valheim | 2건 | 80.2 ~ 92.5h | 1.2배 |
| Dead Cells | 2건 | 13.7 ~ 21.2h | 1.6배 |
| Dave the Diver | 4건 | 21.8 ~ 34.4h | 1.6배 |
| Slay the Spire | 3건 | 17.8 ~ 30.8h | 1.7배 |

같은 게임이라도 패치마다 구간의 시간 범위가 달라집니다. 목업이 `range: '0 – 46h'` 처럼 실제 시간을 화면에 표시하므로 혼란은 없습니다.

**대안(누적 기준)을 채택하지 않은 이유**

게임 전체 누적 리뷰로 경계를 고정하면 패치 간 비교가 가능해지지만, 창 리뷰가 특정 밴드로 몰립니다.

```
누적 기준 편중도 (최대밴드 / 최소밴드)
  중앙 1.5배 · 최대 2.3배

최악 사례 · Dave the Diver 08-10
  15.2% / 21.2% / 29.4% / 34.2%
```

치명적이지는 않으나 창 기준이 항상 균등하고, 패치 진단 화면에서는 "이 패치에 반응한 사람들을 4등분"하는 의미가 더 자연스럽습니다. 패치 간 밴드 비교 기능은 목업에 없습니다.

## ③ 언어별 반응 분포

| 항목 | 값 |
| --- | --- |
| 통계 (긍정률) | 패치 전 7일 / 후 7일 각각 → before / after |
| 대표 리뷰 창 | 패치 후 7일 |
| 언어 선정 | 그 게임에서 가장 많이 작성된 언어 5개 |
| 단위 | 게임 × 최신 패치 × 언어 5개 |
| 선정 | 언어별 좋아요 순 5건 |
| AI 요약 | 언어마다 1개 |
| 원문 표시 | 언어별 상위 2건 |

목업 초안의 "리뷰 비중 × 긍정률 하락 폭 기준 상위 5개" 는 사용하지 않습니다. 작성 수 기준으로 단순화합니다.

### 5건을 못 채우는 언어는 제외합니다

상위 5개 언어를 뽑되, 패치 후 7일에 30바이트 초과 리뷰가 5건 미만인 언어는 화면에서 뺍니다. 표시되는 언어 수가 게임마다 달라집니다.

```sql
SELECT review_language, COUNT(*) AS n
FROM review
WHERE appid = ?
  AND timestamp_updated >= :patch_date
  AND timestamp_updated <  :patch_date + INTERVAL '7 days'
  AND LENGTH(review_text) > 30
  AND review_language IN (:top5_languages)
GROUP BY review_language
HAVING COUNT(*) >= 5
ORDER BY n DESC;
```

**실측 — 게임 16개 기준**

| 살아남는 언어 수 | 게임 수 |
| --- | --- |
| 5개 | 10 |
| 4개 | 2 |
| 1개 | 2 |
| 0개 | 2 |

패치 후 7일 리뷰가 150건 이상이면 5개가 다 남습니다. 100건 근처에서 4개, 50건 미만이면 1개 이하가 됩니다.

| 게임 | 패치 후 7일 리뷰 | 살아남는 언어 |
| --- | --- | --- |
| CS2 | 1,696 | 5 |
| HELLDIVERS 2 | 1,061 | 5 |
| Hades | 172 | 5 |
| Slay the Spire | 97 | 4 |
| Dead Cells | 92 | 4 |
| Ostranauts | 44 | 1 |
| Across the Obelisk | 15 | 1 |
| Rise to Ruins | 3 | 0 |

**0개인 경우 언어별 섹션 자체를 숨깁니다.** 리뷰가 1~3건인 패치는 언어별로 나눌 것이 물리적으로 없습니다.

**밴드도 같은 문제가 있습니다.** 패치 후 7일 리뷰가 40건 미만이면 밴드별 5건을 못 채웁니다. 같은 규칙(5건 미만 밴드 제외)을 적용합니다.

**언어별 리뷰 수는 대부분 적습니다**

```
게임 × 언어 조합 59개 기준
  중앙값 18건 · 평균 41건 · 최대 311건
  10건 이하 35.6% · 20건 이하 61.0% · 50건 이하 72.9%
```

5건을 뽑기에는 충분하지만, 리뷰가 5건 미만인 언어는 요약을 생략하고 원문만 표시하는 것을 검토해야 합니다.

## 과거 패치는 Daily 탭에서만 조회됩니다

패치 네비게이터(◀ 3/12 ▶)는 Daily 탭에만 있습니다. **다른 탭은 최신 패치 고정입니다.**

| 탭 | 과거 패치 지원 | 보여주는 것 |
| --- | --- | --- |
| Daily | **지원** | 일별 리뷰 수 · 첫 작성/수정 비율 · 긍정률 |
| Reviews | 안 함 | 최신 패치의 대표 리뷰 5건 |
| Topics | 안 함 | 최신 패치의 밴드별 통계 + 대표 리뷰 + 요약 |
| Lang | 안 함 | 최신 패치의 언어별 통계 + 대표 리뷰 + 요약 |

이 결정이 저장량을 크게 줄입니다.

### 테이블별로 필요한 범위가 갈립니다

| 테이블 | 범위 | 이유 |
| --- | --- | --- |
| game_daily_stat | 전체 기간 | Daily 탭이 과거 패치 차트를 그림 |
| patch_review_stat | **모든 패치** | 유사 사례 검색이 과거 패치 수치를 사용 |
| game_playtime_band_stat | **최신 패치만** | Topics 탭이 최신만 지원 |
| language_stat | **최신 패치만** | Lang 탭이 최신만 지원 |
| review_repr | 최신 패치만 | — |
| patch_summary | 최신 패치만 | — |

`patch_review_stat` 만 모든 패치를 담습니다. 유사 사례 검색이 "Path of Exile 3.15 패치는 −40.8%p 였다" 같은 과거 수치를 쓰기 때문입니다. 대신 수치만 담는 가벼운 테이블입니다.

### 과거 패치는 집계 테이블만으로 처리됩니다

Daily 탭에서 패치를 과거로 넘기면 그 시점의 차트만 다시 그립니다.

```sql
SELECT stat_date, channel, review_count, positive_rate
FROM game_daily_stat
WHERE appid = ?
  AND stat_date BETWEEN :patch_date - 7 AND :patch_date + 7;
```

목업 데이터가 이 구조와 정확히 맞습니다.

```js
days: [{ d: '04/02', f: 48, e: 9, r: 68.4 }, ...]
                        ↑첫작성  ↑수정  ↑긍정률
```

`f` 와 `e` 가 `game_daily_stat.channel` (first / edited) 입니다. **대표 리뷰를 조회하지 않습니다.**

## 적재량 산정

진단 대상 게임 8,239개 (리뷰 1,000건 이상), 게임당 최신 패치 1건 기준입니다.

### DB 에 적재할 리뷰 행 수

대표 리뷰만 골라 넣지 않고 **최신 패치의 패치 후 7일 리뷰를 전량** 넣습니다. Reviews 탭의 리뷰 검색 기능이 대표 5건만으로는 동작하지 않기 때문입니다.

```
리뷰 검색 — 불만·만족 요소 토픽 5종으로 리뷰를 좁혀 봅니다
```

5건 중 밸런스 토픽을 거르면 1~2건이 남습니다. 검색이라 할 수 없습니다.

| 게임 리뷰 수 | 게임 수 | 7일 창 추정 | 소계 |
| --- | --- | --- | --- |
| 1,000 ~ 10,000 | 6,482 | 약 20건 | 13만 |
| 10,000 ~ 100,000 | 1,529 | 약 150건 | 23만 |
| 100,000 이상 | 228 | 약 800건 | 18만 |
| **합계** | **8,239** | | **약 54만 행** |

```
전체 리뷰      1.5억 건
DB 적재분      약 54만 건  =  0.36%
```

상위 N건으로 자를 이유가 없습니다. 8,239개 중 79%가 리뷰 1만 건 미만이라 7일 창에 수십 건뿐이고, **상한을 걸어도 행 수가 거의 같습니다.** 전량 저장이 더 단순하고 화면 표기도 정직해집니다.

**대표 리뷰는 별도로 저장하지 않고 쿼리로 뽑습니다.**

```sql
-- 리뷰 탭 대표 5건
SELECT * FROM patch_review WHERE appid = ?
ORDER BY votes_up DESC, LENGTH(review_text) DESC LIMIT 5;

-- 밴드별 5건
SELECT * FROM patch_review WHERE appid = ? AND band = 3
ORDER BY votes_up DESC, LENGTH(review_text) DESC LIMIT 5;

-- 언어별 5건
SELECT * FROM patch_review WHERE appid = ? AND review_language = 'koreana'
ORDER BY votes_up DESC, LENGTH(review_text) DESC LIMIT 5;
```

### AI 요약 개수

| 화면 | 게임당 | 계산 | 개수 |
| --- | --- | --- | --- |
| ① 리뷰 탭 | 1개 | 8,239 | 0.8만 |
| ② 플레이타임 구간별 | 4개 | 8,239 × 4 | 3.3만 |
| ③ 언어별 | 5개 | 8,239 × 5 | 4.1만 |
| 합계 | **10개** | | **약 8.2만 개** |

### 요약 입력 토큰

리뷰 5건 × 평균 484바이트 ÷ 2.5 = 약 970 토큰. 로컬 7B 모델 컨텍스트에 충분히 들어갑니다.

## AI 요약 생성 — 배치로 미리 전량 생성

8.2만 개는 미리 다 만들 수 있는 규모입니다.

```
로컬 LLM 초당 1.3~2.7건
8.2만 개  →  8.5~17시간 (1회성)
```

이후 갱신은 **그날 새 패치가 나온 게임만** 대상이라 하루에 수십~수백 개 수준입니다.

**온디맨드 생성과 source_hash 캐시 무효화는 필요 없습니다.** 247만 개를 미리 못 만들어서 도입하려던 장치였는데, 최신 패치만 다루기로 하면서 전제가 사라졌습니다.

```sql
CREATE TABLE patch_summary (
    appid        BIGINT      NOT NULL,
    gid          VARCHAR(20) NOT NULL,   -- 어느 패치 기준인지 기록용
    scope        VARCHAR(20) NOT NULL,   -- review_tab / band / language
    scope_key    VARCHAR(20) NOT NULL,   -- '' / Q1~Q4 / 언어코드
    summary      TEXT        NOT NULL,
    generated_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (appid, scope, scope_key)
);
```

## 갱신 주기

| 대상 | 주기 | 방식 |
| --- | --- | --- |
| 집계 테이블 | 매일 전량 재계산 | 수정일 기준이라 과거 숫자가 계속 변함 |
| patch_review | 매일 전량 교체 | appid 단위 삭제 후 삽입 |
| AI 요약 | **대표 리뷰가 바뀐 것만** | source_ids 비교 후 재생성 |

### AI 요약은 왜 조건부로 도는가

매일 전량 재수집하므로 `patch_review` 가 매일 갱신됩니다. 그러면 대표 리뷰 상위 5건도 바뀔 수 있고, 바뀌면 요약도 다시 만들어야 합니다.

```
패치 후 0~7일   새 리뷰 유입 + 좋아요 증가   →  자주 바뀜
패치 후 7일~    창은 닫혔지만 좋아요는 계속   →  가끔 바뀜
새 패치         완전히 새로 뽑음             →  전부 바뀜
```

**새 패치가 나오지 않아도 요약이 바뀝니다.**

그렇다고 매일 전부 다시 만들 수는 없습니다.

```
8.2만 개 × 매일  =  8.5시간 × 매일
```

임베딩 배치(4.6시간)도 같은 GPU 를 쓰므로 감당이 안 됩니다.

### source_ids 로 비교합니다

```sql
CREATE TABLE patch_summary (
    appid        BIGINT      NOT NULL,
    scope        VARCHAR(20) NOT NULL,   -- review_tab / band / language
    scope_key    VARCHAR(20) NOT NULL,   -- '' / Q1~Q4 / 언어코드
    gid          VARCHAR(20) NOT NULL,
    summary      TEXT        NOT NULL,
    source_ids   VARCHAR(80) NOT NULL,   -- 대표 리뷰 5건의 review_id
    generated_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (appid, scope, scope_key)
);
```

해시 대신 **리뷰 ID 5개를 그대로 저장**합니다. 디버깅할 때 어떤 리뷰로 만든 요약인지 바로 보이고, 길이도 80바이트면 충분합니다.

### 매일 도는 순서

```
① patch_review 갱신 완료
② 게임마다 대표 리뷰 5건을 다시 뽑음          SQL LIMIT 5
③ source_ids 와 비교
     같으면  →  건너뜀
     다르면  →  LLM 호출해서 요약 재생성
```

**②는 인덱스로 5행 읽는 쿼리입니다.** 8,239 게임 × 10조합 = 8.2만 번 실행해도 몇 분입니다. 비싼 것은 ③의 LLM 호출뿐입니다.

### 하루 재생성량 추정

```
패치 주기 평균 13.5일  →  하루 약 610개 게임이 새 패치
                          요약 10개씩 전부 재생성  →  6,100개

패치 후 7일 이내 게임도 대표 리뷰가 흔들림
                          →  추가 수천 개
```

**하루 1~2만 개, 1~2시간**으로 예상됩니다. 임베딩 배치와 순차로 돌리면 하룻밤에 들어갑니다.

정확한 값은 운영해보며 재야 합니다. 재생성 건수가 예상보다 많으면 대표 리뷰 순위가 자주 뒤집힌다는 뜻이니, 그때는 정렬에 안정성을 더하는 것을 검토합니다. 예를 들어 좋아요 차이가 1~2표뿐일 때는 기존 순위를 유지하는 식입니다.

### 스테이징 테이블 교체는 필요 없습니다

`patch_review` 는 `appid` 단위로 삭제 후 삽입합니다. 게임 하나에 평균 66행이라 대량 삭제가 아니고, PostgreSQL 이 부풀지 않습니다.

```sql
BEGIN;
DELETE FROM patch_review WHERE appid = ?;
INSERT INTO patch_review (...) VALUES ...;
COMMIT;
```

### 과거 대표 리뷰는 남지 않습니다

새 패치가 나오면 이전 패치의 창 리뷰가 통째로 교체됩니다. 나중에 과거 패치 대표 리뷰가 필요해지면 HDFS 원본에서 다시 뽑아야 합니다. 되돌릴 수 없는 결정은 아니지만 재계산이 필요합니다.

## 스키마 영향

### game_playtime_band_stat — 최신 패치만

```sql
CREATE TABLE game_playtime_band_stat (
    appid           BIGINT      NOT NULL,
    band            SMALLINT    NOT NULL,   -- 1~4
    phase           VARCHAR(10) NOT NULL,   -- before / after
    gid             VARCHAR(20) NOT NULL,   -- 어느 패치 기준인지 기록용
    band_min_hours  NUMERIC(8,2),
    band_max_hours  NUMERIC(8,2),
    median_playtime NUMERIC(8,2),
    review_count    INTEGER     NOT NULL,
    positive_rate   NUMERIC(5,2),
    min_sample_ok   BOOLEAN     NOT NULL,
    PRIMARY KEY (appid, band, phase)
);
```

Topics 탭이 최신 패치만 지원하므로 `gid` 는 PK 에서 빠집니다. **게임당 8행(4밴드 × 2phase)으로 고정**됩니다.

행 수는 8,239 × 8 = 약 6.6만 행입니다. 패치별로 쌓던 이전 계산(165만 행)에서 25배 줄었습니다.

밴드 경계는 패치마다 다시 계산하므로 새 패치가 나오면 덮어씁니다.

### language_stat — 최신 패치만

같은 이유로 `gid` 가 PK 에서 빠집니다.

```sql
PRIMARY KEY (appid, language)
gid VARCHAR(20) NOT NULL   -- 기록용
```

8,239 × 5언어 = 약 4.1만 행입니다.

### patch_review_stat — 모든 패치 유지

유사 사례 검색이 과거 패치 수치를 쓰므로 이 테이블만 패치별로 쌓습니다.

```sql
PRIMARY KEY (gid)
appid, before_count, after_count, before_positive, after_positive,
delta, outcome, patch_interval_days, next_notice_ratio, min_sample_ok
```

### patch_review — 신설

최신 패치의 패치 후 7일 리뷰를 전량 담습니다. 대표 리뷰 · 밴드별 · 언어별 · 리뷰 검색이 모두 이 한 테이블에서 나옵니다.

```sql
CREATE TABLE patch_review (
    appid       BIGINT      NOT NULL,
    review_id   BIGINT      NOT NULL,
    gid         VARCHAR(20) NOT NULL,   -- 어느 패치 기준인지 기록용
    review_text TEXT        NOT NULL,
    voted_up    BOOLEAN     NOT NULL,
    votes_up    INTEGER     NOT NULL,
    is_edited   BOOLEAN     NOT NULL,
    playtime_at_review INTEGER     NOT NULL,
    review_language    VARCHAR(20) NOT NULL,
    band        SMALLINT,               -- 1~4. 밴드 계산 결과
    topics      VARCHAR(100),           -- 쉼표 구분. HDFS 에서 그대로 가져옴
    created_at  BIGINT      NOT NULL,
    updated_at  BIGINT      NOT NULL,
    PRIMARY KEY (appid, review_id)
);

CREATE INDEX idx_pr_votes    ON patch_review (appid, votes_up DESC);
CREATE INDEX idx_pr_band     ON patch_review (appid, band, votes_up DESC);
CREATE INDEX idx_pr_language ON patch_review (appid, review_language, votes_up DESC);
```

**`topics` 컬럼이 있어 조인이 필요 없습니다.** HDFS 에서 대표 리뷰를 뽑을 때 토픽이 함께 딸려옵니다. 목업의 리뷰 카드에 붙는 태그가 이 컬럼입니다.

```js
{ kind: '단점', helpful: '412', tags: ['밸런스/너프', '상위 난이도'] }
                                 ↑ topics 컬럼
```

**`review_repr` 테이블은 만들지 않습니다.** 대표 리뷰를 미리 골라 저장하는 대신 창 리뷰를 전량 넣고 정렬로 뽑습니다. 인덱스 세 개면 세 화면이 모두 즉시 응답합니다.

**새 패치가 나오면 그 게임의 행을 통째로 교체합니다.** `appid` 단위 삭제 후 삽입이므로 게임당 행 수가 누적되지 않습니다.
