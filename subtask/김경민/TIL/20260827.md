# TIL 2026-08-27 (목)

## 사전학습 — 역색인 응용과 Top-K 검색

### 역색인을 이용한 공통 아이템 개수 계산

- 입력은 `레코드ID + 아이템 목록`이며, 두 레코드가 공통으로 가진 아이템 개수를 구했다.
- 1단계 Mapper는 각 아이템에 대해 `(아이템, 레코드ID)`를 출력하여 역색인을 만들었다.
- 1단계 Reducer는 같은 아이템을 가진 레코드 ID들을 모아 가능한 모든 레코드 쌍 `(rid1,rid2)`에 값 `1`을 출력했다.
- 레코드 쌍은 작은 ID가 먼저 오도록 정규화하여 `(0,1)`과 `(1,0)`이 따로 집계되지 않게 했다.
- 2단계 Mapper가 레코드 쌍과 `1`을 다시 읽고, Reducer가 합계를 계산하여 두 레코드의 공통 아이템 개수를 만들었다.
- `out1`은 역색인을 이용해 생성한 중간 레코드 쌍이고, `out2`가 공통 아이템 개수를 합산한 최종 결과다.

### Top-K 최근접 포인트 검색

- 질의 포인트와 각 레코드 사이의 유클리드 거리를 계산하고 거리가 가장 작은 K개 레코드를 찾았다.
- 레코드 ID를 파티션 수로 나눈 나머지로 데이터를 분배했다.
- 1단계에서는 각 파티션 Reducer가 로컬 Top-K를 계산했다.
- 2단계에서는 각 파티션의 후보를 하나의 Reducer로 모아 전역 Top-K를 계산했다.

### Max-Heap을 사용하는 이유

- 가장 가까운 K개만 유지할 때는 현재 후보 중 **가장 먼 값**을 빠르게 찾아야 한다.
- Max-Heap의 루트에는 후보 중 가장 큰 거리, 즉 현재 Top-K의 탈락 기준이 놓인다.
- 새 거리가 루트보다 작으면 루트를 제거하고 새 후보를 넣으며, 더 크거나 같으면 무시한다.
- Java의 `PriorityQueue`와 `Comparable` 비교 규칙을 이용해 Max-Heap처럼 동작하도록 구현했다.

### 2단계가 필요한 이유

- 각 파티션에서 구한 Top-K는 해당 파티션 내부에서만 가장 가까운 결과다.
- 전체 데이터 기준 최종 Top-K를 얻으려면 모든 로컬 후보를 다시 모아 한 번 더 비교해야 한다.
- 최종 출력에서 질의점 `(1,1)`에 가까운 세 점이 거리 `1.0`, `1.0`, `1.414...`로 나온 것을 확인했다.

### 실습 중 확인한 주의점

- Java는 대소문자를 구분하므로 식별자 오타가 컴파일 오류를 만든다.
- 탭 문자를 찾을 때는 문자열 `"\t"`를 사용해야 한다.
- 두 번째 단계의 Reducer 수를 1개로 두어야 전역 후보가 한곳에 모이고 결과 파일도 하나가 된다.

### 핵심 정리

> 대용량 Top-K는 각 파티션에서 후보를 줄인 뒤 전역에서 한 번 더 합치는 2단계 구조로 처리하고, Max-Heap으로 현재 후보 중 가장 나쁜 값을 빠르게 교체한다.

### 6. 키워드 매칭에는 문맥 조건이 필요하다

롤백(되돌리기) 탐지에서 오탐이 발생했다.

| 게임 | 키워드만 | **문맥 조건 추가** |
|---|---|---|
| Slay the Spire 2 | 4건 | 1건 |
| Helldivers 2 | 2건 | 2건 |
| **Path of Exile 2** | **1건 (오탐)** | **0건** |

**오탐 원인**: POE2 패치노트의 `Reverse Cleave`는 보스 스킬 이름인데 `reverse`가 포함되어 롤백으로 분류됐다.

게임 도메인에서 `restore`(체력 회복), `undo`(되돌리기 기능), `reverse`(스킬명)는 일상적으로 사용되는 표현이다.

**해결**: 되돌림 동사와 이전 상태 참조 표현(`pre-N.N`, `previous`, 버전 번호)을 같은 문장 내에서 동시에 요구한다.

```
"Reverse Cleave"                            → 제외됨
"reverted back to their pre-0.109.0 versions"  → 탐지됨
"Reverted the change made in the previous"     → 탐지됨
```

**트레이드오프**: 정밀도가 향상되지만 재현율이 하락한다(STS2 4건→1건). 잘못된 "롤백 있음" 표시보다 "정보 없음"이 안전하므로 정밀도를 우선했다.

동일한 원리로 베타 테스트 판정 정규식에서도 `preview`를 제외했다. POE2의 `Patch Preview`(패치 예고) 3건이 베타로 오탐됐으며, `beta` 자체는 오탐이 없었다.

### 8. 단일 스냅샷으로는 이탈을 측정할 수 없다

`playtime_forever - playtime_at_review`로 "리뷰 작성 후 플레이 중단 여부"를 측정했다.

초기 결과는 다음과 같았다.

| 패치일(8/14) | 중단율 |
|---|---|
| 부정 리뷰 작성자 | **22.7%** |
| 긍정 리뷰 작성자 | 2.5% |

9배 차이가 나타났으나, 다른 날짜와 비교하면 값이 불안정했다.

| 구간 | 긍정 리뷰 "중단율" |
|---|---|
| 08-14 | 25.9% |
| 08-15 | **43.8%** |
| 08-05~08 | 16.0% |
| 07-20~25 | 10.5% |

긍정 리뷰 작성자의 43.8%가 중단했다는 결과는 타당하지 않다.

**원인**: `playtime_forever`와 `last_played`는 조회 시점 기준 값이다. 8/15 작성 리뷰는 수집까지 10일이 경과했으므로 재접속 기회가 물리적으로 적다. 반면 7/20 리뷰는 36일이 경과했다.

7일 컷오프를 적용해도 이 편향은 제거되지 않았다. 각 리뷰 시점으로부터 정확히 N일 후의 상태가 필요한데, 확보된 데이터는 단일 스냅샷이다.

**결론**: 절대 이탈률은 측정할 수 없다. 동일 날짜 코호트 내 긍정/부정 비교는 유효하다(경과 시간 동일). 평시 부정 리뷰 작성자가 긍정 대비 3.5~3.7배 높은 중단율을 보였다.

정확한 측정은 일별 스냅샷 축적으로만 가능하며, 과거 소급은 원리적으로 불가능하다.

### 11. 검색 API와 인기 목록은 다른 데이터를 반환한다

대상 게임 목록 생성을 위해 `storesearch` API에 "roguelike"를 조회했으나, 이름에 해당 단어가 포함된 소규모 신작만 반환됐다.

```
Combolands: Roguelike Citybuilder (303건)
RACCOIN: Coin Pusher Roguelike (4,573건)

```

리뷰 2만 건 이상 필터 적용 시 통과 게임이 0개였다.

**해결**: SteamSpy 인기 목록과 상점 검색 결과 페이지(`search/results/?infinite=1`)에서 `data-ds-appid`를 추출하는 방식으로 변경했다. 이후 CS2, Dota 2, PUBG 등 인기 게임이 정상 확보됐다.

### 12. 채널 분리 교차검증 — 표본 505건

채널 분리의 타당성을 독립 지표로 교차검증했다.

| 패치일 (505건) | 긍정률 | 플레이 이력 중앙값 |
|---|---|---|
| 첫 작성 (`created==updated`) | 46.7% | **118.8시간** |
| **수정된 리뷰** (`created<updated`) | **13.9%** | **194.7시간** |

**독립 지표(`playtime_at_review`)로 분리해도 동일한 방향이 나타났다.**

| 플레이타임 기준 | 긍정률 |
|---|---|
| 짧은 플레이 | 46.2% |
| **긴 플레이** | **21.0%** |

평시 구간(1,945건)에서도 재현됐다(첫 작성 76.1% vs 수정 46.2%). 수정된 리뷰의 67.7%가 긴 플레이 그룹인데, 첫 작성은 38.2%였다.

**동시에 확인된 한계:**
- **첫 작성 그룹도 플레이 이력 중앙값이 118.8시간**이므로 "신규 유저"로 해석할 수 없다
- **수정 방향을 알 수 없다** — 긍정→부정 전환인지, 원래 부정이었는데 내용만 수정한 것인지 단일 스냅샷으로는 구분 불가
- 오타 수정도 `timestamp_updated`를 갱신한다

**대응**: 명칭을 "첫 작성 리뷰 / 수정된 리뷰"(채널 기준)로 변경하고, 해석 범위를 "수정 채널의 부정 비중 증가"까지로 한정했다.
