# PoC

## PoC(Proof of Concept)란

PoC(Proof of Concept, 개념 증명)는 새로운 아이디어나 기술이 실제로 구현 가능한지를 작은 범위에서 검증하는 과정이다. 완성된 제품을 만드는 것이 목적이 아니라, 본격적인 개발에 들어가기 전에 핵심 가설과 기술적 불확실성을 빠르게 확인하는 것이 목적이다.

PoC를 통해 다음과 같은 질문에 답할 수 있다.

- 선택한 기술로 핵심 기능을 구현할 수 있는가?
- 예상한 성능, 보안, 확장성 등의 기준을 만족할 수 있는가?
- 기존 시스템이나 외부 서비스와 연동할 수 있는가?
- 프로젝트를 계속 진행할 만큼 충분한 가치가 있는가?

PoC는 제한된 기간과 자원으로 핵심 기능만 검증하며, 사용자 경험이나 코드 품질, 운영 환경의 완성도는 우선순위가 낮다. 검증 결과는 성공과 실패로만 구분하기보다, 확인한 사실과 남아 있는 위험 요소를 정리해 다음 의사결정의 근거로 활용해야 한다.

PoC는 프로토타입이나 파일럿과 목적이 다르다. 프로토타입은 화면과 사용 흐름 등 제품의 형태를 확인하는 데 중점을 두고, 파일럿은 실제 사용자와 운영 환경에서 제품을 제한적으로 적용해 보는 단계이다. 반면 PoC는 아이디어의 기술적 실현 가능성을 확인하는 데 초점을 둔다.

## PoC의 단계

1. **문제와 가설 정의**
   해결하려는 문제와 검증할 가설을 명확하게 정의한다. 예를 들어, "새로운 검색 엔진을 적용하면 응답 시간을 1초 이내로 줄일 수 있다"와 같이 측정 가능한 형태로 작성한다.

2. **범위 설정**
   핵심 가설을 검증하는 데 필요한 최소 기능만 선정한다. 범위가 커지면 시간과 비용이 증가하고 검증의 초점이 흐려질 수 있으므로 부가 기능은 제외한다.

3. **성공 기준 수립**
   성능, 정확도, 비용, 개발 기간 등 객관적으로 판단할 수 있는 지표를 정한다. 성공 기준은 구현 전에 합의해야 결과를 자의적으로 해석하는 일을 방지할 수 있다.

4. **구현 및 실험**
   정해진 범위 안에서 최소한의 기능을 구현하고, 실제 사용 환경과 유사한 조건에서 실험한다. 이 과정에서 사용한 기술, 설정, 제약 사항도 함께 기록한다.

5. **결과 분석**
   실험 결과를 성공 기준과 비교하고, 기술적 한계와 위험 요소를 분석한다. 예상과 다른 결과가 나왔다면 원인과 추가로 검증할 항목을 정리한다.

6. **의사결정 및 문서화**
   결과를 바탕으로 본 개발 진행, 추가 PoC 수행, 기술 변경, 프로젝트 중단 중 하나를 결정한다. 검증 방법과 결과, 한계, 다음 작업을 문서로 남겨 이후 개발의 근거로 활용한다.

# Single-flight 패턴

Single-flight는 동일한 작업이 동시에 여러 번 요청되었을 때 실제 작업은 한 번만 수행하고, 나머지 요청은 그 하나의 실행 결과를 함께 기다리도록 만드는 패턴이다.

인증 처리에서는 Access Token이 만료된 순간 여러 API 요청이 동시에 `401 Unauthorized` 응답을 받을 수 있다. 각 요청이 개별적으로 토큰 갱신을 시도하면 동일한 Refresh Token으로 여러 번 갱신 요청을 보내게 된다. 이때 첫 번째 갱신만 성공하고 나머지는 실패하거나, Refresh Token 재사용으로 감지되어 세션 전체가 취소될 수 있다.

이를 방지하기 위해 토큰 갱신 중인 Promise를 공유한다.

```ts
let refreshPromise: Promise<void> | null = null;

async function refreshOnce() {
  if (!refreshPromise) {
    refreshPromise = refreshAccessToken().finally(() => {
      refreshPromise = null;
    });
  }

  return refreshPromise;
}
```

전체 흐름은 다음과 같다.

1. 여러 API 요청이 동시에 `401` 응답을 받는다.
2. 첫 번째 요청이 갱신 Promise를 생성한다.
3. 나머지 요청은 새 갱신 요청을 만들지 않고 같은 Promise를 기다린다.
4. 갱신이 성공하면 각 요청을 한 번만 재시도한다.
5. 갱신이 실패하면 로그인 상태를 정리하고 사용자에게 재로그인을 요청한다.

무한 재시도를 막기 위해 원래 요청에 재시도 여부를 표시해야 하며, 로그인이나 토큰 갱신 API 자체는 인터셉터의 갱신 대상에서 제외해야 한다. 또한 이 방식은 하나의 탭처럼 동일한 자바스크립트 실행 환경 안에서만 요청을 합친다. 서로 다른 탭의 동시 갱신은 별도의 동기화가 필요하다.

# Refresh Token Rotation과 reuse detection

Refresh Token Rotation은 Refresh Token을 사용할 때마다 기존 토큰을 폐기하고 새로운 Refresh Token을 발급하는 방식이다. 탈취된 토큰이 오랫동안 반복 사용되는 위험을 줄일 수 있다.

예를 들어 `RT1`으로 갱신 요청을 보내면 서버는 `RT1`을 사용 완료 상태로 변경하고 새로운 `RT2`를 발급한다. 이후 정상 클라이언트는 `RT2`만 사용해야 한다.

```text
로그인 → RT1 발급
RT1 사용 → RT1 폐기 + RT2 발급
RT2 사용 → RT2 폐기 + RT3 발급
```

reuse detection은 이미 사용되어 폐기된 Refresh Token이 다시 제출되는 상황을 탐지하는 것이다. `RT1`로 `RT2`가 발급된 뒤 누군가 다시 `RT1`을 사용한다면, 서버는 토큰이 복제되었을 가능성이 있다고 판단한다. 이 경우 해당 토큰 하나만 거부하는 것이 아니라 같은 로그인에서 파생된 토큰 패밀리 전체를 폐기하고 재로그인을 요구하는 것이 일반적이다.

서버는 다음 정보를 기준으로 토큰의 상태를 관리할 수 있다.

- 토큰의 고유 식별자와 해시값
- 사용자 및 세션 식별자
- 토큰 패밀리 식별자
- 발급 시각과 만료 시각
- 사용·폐기 여부와 다음 토큰의 식별자

토큰 검증, 기존 토큰 폐기, 새 토큰 발급은 하나의 원자적 연산으로 처리해야 한다. 동시에 같은 Refresh Token이 들어왔을 때 둘 다 성공하면 Rotation의 의미가 사라지기 때문이다. 클라이언트의 Single-flight 패턴은 정상적인 동시 요청 때문에 reuse detection이 발생하는 상황을 줄여준다.

Refresh Token은 자바스크립트에서 직접 읽기 어려운 `HttpOnly`, `Secure`, 적절한 `SameSite` 속성의 쿠키에 저장하는 것이 안전하다. Rotation과 reuse detection은 토큰 탈취 위험을 완전히 없애는 기능이 아니라, 탈취된 토큰의 사용 기간을 제한하고 침해 사실을 탐지하기 위한 방어 계층이다.

# BroadcastChannel을 이용한 멀티탭 인증 동기화

브라우저의 각 탭은 서로 독립된 자바스크립트 실행 환경을 가진다. 따라서 한 탭에서 로그인, 로그아웃 또는 토큰 갱신이 발생해도 다른 탭의 메모리 상태는 자동으로 변경되지 않는다. `BroadcastChannel`을 사용하면 같은 출처(origin)의 탭끼리 인증 상태 변경 이벤트를 전달할 수 있다.

```ts
const authChannel = new BroadcastChannel("auth");

authChannel.postMessage({ type: "LOGOUT" });

authChannel.onmessage = ({ data }) => {
  if (data.type === "LOGOUT") {
    clearAuthState();
    redirectToLogin();
  }
};
```

주로 다음과 같은 이벤트를 동기화한다.

- `LOGIN`: 다른 탭이 로그인 상태와 사용자 정보를 다시 조회한다.
- `TOKEN_REFRESHED`: 다른 탭이 오래된 Access Token을 버리고 최신 인증 상태를 다시 확인한다.
- `LOGOUT`: 모든 탭이 메모리의 인증 정보를 제거하고 로그인 화면으로 이동한다.
- `SESSION_REVOKED`: reuse detection 등으로 세션이 폐기되었음을 모든 탭에 알린다.

채널 메시지에는 Access Token이나 Refresh Token 자체를 담지 않는 것이 좋다. `BroadcastChannel`은 같은 출처의 모든 브라우징 컨텍스트가 메시지를 받을 수 있으므로, 메시지는 인증 상태가 변경되었다는 신호로만 사용하고 각 탭이 서버를 통해 상태를 다시 확인하도록 한다. Refresh Token이 `HttpOnly` 쿠키에 있다면 자바스크립트가 토큰 값을 읽거나 전달할 필요도 없다.

`BroadcastChannel`만으로 여러 탭의 갱신 요청이 자동으로 하나가 되는 것은 아니다. 멀티탭 환경에서 완전한 Single-flight가 필요하다면 한 탭만 갱신을 담당하도록 리더 또는 잠금을 정하고, 나머지 탭은 `TOKEN_REFRESHED`나 `REFRESH_FAILED` 이벤트를 기다리는 방식이 추가로 필요하다. 메시지를 받지 못하는 경우에 대비해 대기 시간 제한을 두고 서버에서 세션 상태를 다시 확인해야 한다.

## BroadcastChannel은 필수인가?

React는 멀티탭 인증 상태를 동기화하는 기능을 별도로 제공하지 않는다. React 애플리케이션의 상태와 자바스크립트 메모리는 탭마다 독립적이기 때문이다. 그러나 다른 탭의 인증 정보를 없애기 위해 반드시 `BroadcastChannel`을 사용해야 하는 것은 아니며, 인증 정보를 어디에 저장했는지에 따라 사용할 수 있는 방법이 달라진다.

### HttpOnly Cookie

같은 출처의 탭은 쿠키를 공유한다. 한 탭의 로그아웃 요청에 대해 서버가 만료된 `Set-Cookie` 헤더를 내려주면 다른 탭에서도 해당 쿠키를 더 이상 사용할 수 없다. 따라서 실제 인증 자격 증명은 모든 탭에서 제거된다.

다만 다른 탭의 React 상태와 화면은 자동으로 갱신되지 않는다. 해당 탭이 다음 API 요청에서 인증 실패를 확인하거나, 별도의 이벤트를 전달받아 인증 상태를 초기화해야 화면에도 로그아웃이 즉시 반영된다.

### localStorage

`localStorage`는 같은 출처의 탭이 데이터를 공유한다. 한 탭에서 인증 정보를 제거하면 다른 탭에서도 그 값을 읽을 수 없으며, 다른 탭에는 `storage` 이벤트가 발생한다. 이를 이용하면 `BroadcastChannel` 없이도 로그아웃 상태를 전달할 수 있다.

```ts
window.addEventListener("storage", (event) => {
  if (event.key === "auth" && event.newValue === null) {
    clearAuthState();
    redirectToLogin();
  }
});
```

`storage` 이벤트는 값을 변경한 탭에는 발생하지 않고 다른 탭에만 발생하므로, 값을 제거한 현재 탭의 상태는 직접 초기화해야 한다. 또한 XSS 공격에 노출될 수 있으므로 장기간 사용하는 Refresh Token을 `localStorage`에 저장하는 것은 피하는 것이 좋다.

### sessionStorage와 메모리

`sessionStorage`와 React 상태, 자바스크립트 메모리는 탭마다 독립적이다. 한 탭에서 다른 탭의 값을 직접 삭제할 수 없으므로 `BroadcastChannel`, `storage` 이벤트를 이용한 신호 전달, SharedWorker 등의 탭 간 통신 수단이 필요하다.

### 정리

- `HttpOnly Cookie`: 로그아웃 시 공유 쿠키는 모든 탭에서 제거되지만 각 탭의 화면 상태는 별도로 갱신해야 한다.
- `localStorage`: 값이 모든 탭에서 제거되며 `storage` 이벤트로 다른 탭의 상태도 갱신할 수 있다.
- `sessionStorage` 또는 메모리: 탭마다 독립적이므로 다른 탭에 로그아웃 이벤트를 전달해야 한다.
- `BroadcastChannel`: 인증 정보를 직접 제거하는 기능이 아니라 `LOGOUT`, `SESSION_REVOKED` 같은 상태 변경 신호를 전달하는 수단이다.

일반적으로 Refresh Token은 `HttpOnly Cookie`에 보관하고, 즉각적인 화면 동기화가 필요하면 `BroadcastChannel`을 사용한다. 미지원 환경에서는 `storage` 이벤트를 대안으로 사용할 수 있다. 어떤 방식을 사용하든 채널이나 이벤트에 토큰 자체를 넣지 않고 상태 변경 신호만 전달하는 것이 안전하다.

세 기술을 함께 적용하면 다음과 같은 인증 흐름을 만들 수 있다.

```text
동시 401 발생
  → Single-flight로 갱신 요청을 하나로 통합
  → 서버가 Refresh Token을 교체하고 재사용 여부를 검사
  → 갱신 결과를 BroadcastChannel로 다른 탭에 전달
  → 모든 탭이 최신 인증 상태를 반영
```
