# E2E 테스트의 기준 정하기

## 무엇을 테스트해야 하는가

Playwright의 기본 개념을 정리하고 나니, API를 사용하는 방법보다 어떤 상황을 테스트로 남길지가 더 중요하다는 생각이 들었다. 버튼을 클릭하고 화면이 나타나는지 확인하는 코드는 작성할 수 있지만, 그것만으로 사용자가 기능을 정상적으로 사용할 수 있다고 판단해도 되는지 고민했다.

예를 들어 등록 버튼이 보이는 것과 실제로 데이터를 등록할 수 있는 것은 다르다. 등록 후 성공 메시지가 표시되더라도 저장된 내용을 다시 조회할 수 없다면 사용자의 목적은 달성되지 않은 것이다.

그래서 E2E 테스트의 기준을 **사용자가 핵심 작업을 끝까지 수행하고, 그 결과를 확인할 수 있는가**로 정했다. 테스트 개수를 늘리기보다 서비스에서 반드시 동작해야 하는 흐름을 먼저 찾아 검증하기로 했다.

```text
사용자의 목적 정의
  → 필요한 시작 상태 준비
  → 실제 사용자 행동 수행
  → 사용자가 확인할 수 있는 결과 검증
```

# 테스트 종류별 역할 분리

처음에는 주요 기능을 모두 Playwright로 검증하면 충분하지 않을까 생각했다. 하지만 계산 함수의 결과나 입력값 조합까지 브라우저에서 확인하면 실행 시간이 길어지고, 실패했을 때 어떤 부분이 문제인지 파악하기도 어려워진다.

따라서 검증하려는 범위에 따라 테스트의 역할을 나누기로 했다.

| 종류 | 검증할 대상 | 예시 |
| --- | --- | --- |
| Unit | 개별 함수와 로직 | 가격 계산, 입력값 검증 |
| Component | 하나의 컴포넌트 동작 | 입력 오류 표시, 버튼 활성화 조건 |
| Integration | 여러 모듈이 연결된 동작 | API 응답에 따른 상태 변경과 화면 반영 |
| E2E | 실제 사용자의 핵심 흐름 | 로그인 후 데이터 생성 및 결과 조회 |

세부 조건은 가능한 한 작은 범위의 테스트에서 확인하고, E2E에서는 각 부분이 연결되었을 때 사용자 흐름이 완성되는지를 확인한다. 같은 검증을 모든 계층에 반복하기보다 각 테스트가 어떤 문제를 발견해야 하는지 구분하는 것이 필요하다고 판단했다.

# 핵심 사용자 흐름과 우선순위

## 기능 이름보다 실패했을 때의 영향을 기준으로 판단하기

모든 기능을 같은 우선순위로 테스트하기는 어렵다. 그래서 기능이 실패했을 때 사용자의 작업이 얼마나 막히는지, 데이터나 권한에 어떤 영향을 주는지를 기준으로 우선순위를 정하기로 했다.

| 우선순위 | 판단 기준 | 예시 |
| --- | --- | --- |
| P0 | 서비스의 핵심 작업이 중단되거나 중요한 데이터·권한 문제가 발생함 | 로그인, 핵심 데이터 생성·조회, 접근 권한 제한 |
| P1 | 주요 작업에 불편을 주거나 일부 사용 흐름이 막힘 | 일반적인 수정·삭제, 검색, 필터링 |
| P2 | 핵심 작업의 완료에 미치는 영향이 상대적으로 작음 | 테마 변경, 보조 설정, 장식적인 효과 |

이 분류를 기능 이름만으로 고정하지는 않기로 했다. 검색이 서비스의 핵심이라면 검색도 P0이고, 수정이 주요 업무라면 수정 기능도 처음부터 검증해야 한다. 권한 제한 역시 단순한 예외 상황으로 미루지 않고 핵심 흐름과 함께 확인한다.

처음에는 로그인, 핵심 데이터 조회, 생성, 주요 변경 작업, 권한 제한을 중심으로 소수의 시나리오부터 작성할 계획이다. 테스트 수를 목표로 삼기보다 중요한 흐름에 빠진 부분이 없는지 확인하는 데 집중한다.

# 하나의 테스트에는 하나의 사용자 목적

테스트를 어디에서 나눌지도 고민했다. 로그인부터 생성, 수정, 삭제까지 하나로 연결하면 전체 흐름을 확인할 수는 있지만, 앞부분에서 실패했을 때 뒤의 기능은 검증하지 못한다. 반대로 클릭 한 번마다 테스트를 나누면 사용자의 목적이 잘 드러나지 않는다.

그래서 하나의 테스트는 하나의 사용자 목적을 설명하도록 구성하기로 했다. 이를 정리할 때는 Given, When, Then을 기준으로 사용한다.

```text
Given: 로그인한 사용자가 있다.
When: 제목과 내용을 입력하고 게시글을 등록한다.
Then: 등록한 게시글의 상세 화면에서 입력한 내용을 확인할 수 있다.
```

테스트 이름에도 시작 조건과 기대 결과가 드러나도록 작성한다.

- `로그인 테스트` → `올바른 계정으로 로그인하면 메인 화면으로 이동한다`
- `게시글 테스트` → `로그인한 사용자가 게시글을 등록하면 작성한 내용을 조회할 수 있다`
- `권한 테스트` → `로그인하지 않은 사용자는 게시글 작성 페이지에 접근할 수 없다`

실패한 테스트 이름만 보고도 어떤 사용자 흐름에 문제가 생겼는지 알 수 있어야 한다.

## 성공을 무엇으로 판단할 것인가

버튼 클릭이 오류 없이 끝났다는 사실만으로 테스트를 통과시키지는 않기로 했다. 데이터 생성 테스트라면 생성된 내용, 수정 테스트라면 변경된 값, 삭제 테스트라면 대상이 더 이상 조회되지 않는 상태를 확인해야 한다.

```ts
import { test, expect } from '@playwright/test';

test('로그인한 사용자가 게시글을 등록하면 작성한 내용을 조회할 수 있다', async ({ page }) => {
  await page.goto('/posts/new');

  await page.getByLabel('제목').fill('E2E 테스트 기준');
  await page.getByLabel('내용').fill('사용자 흐름을 기준으로 검증한다.');
  await page.getByRole('button', { name: '등록', exact: true }).click();

  await expect(page).toHaveURL(/\/posts\/\d+$/);
  await expect(
    page.getByRole('heading', { name: 'E2E 테스트 기준', exact: true }),
  ).toBeVisible();
  await expect(
    page.getByText('사용자 흐름을 기준으로 검증한다.', { exact: true }),
  ).toBeVisible();
});
```

위 코드는 테스트 기준을 구체화한 예시이다. 인증 상태와 `baseURL`이 준비되어 있고, 등록 후 숫자 ID를 사용하는 상세 경로로 이동한다고 가정한다. 실제 적용 시에는 서비스의 경로와 화면에 맞추고, 생성한 데이터의 정리도 함께 구성해야 한다.

하나의 사용자 목적을 검증한다고 해서 Assertion을 하나만 사용해야 하는 것은 아니다. 목적이 달성되었는지 판단하는 데 필요한 결과를 함께 확인한다. 저장이 중요한 기능은 새로고침이나 재조회 후에도 내용이 유지되는지 확인해 일시적인 화면 상태와 실제 저장 결과를 구분하기로 했다.

# 테스트의 준비 과정과 검증 대상 분리

## 로그인과 데이터 생성은 필요한 경우에만 UI로 수행하기

게시글 수정 테스트를 실행할 때마다 로그인 화면과 게시글 작성 화면을 거치면, 수정과 직접 관련 없는 기능의 실패에도 영향을 받게 된다. 그래서 검증 대상과 사전 준비를 분리하기로 했다.

```text
로그인 테스트
  → UI로 로그인하고 인증 결과 검증

게시글 작성 테스트
  → 인증 상태 준비
  → UI로 게시글 작성 및 결과 검증

게시글 수정 테스트
  → 인증 상태 준비
  → API로 수정할 게시글 생성
  → UI로 수정 및 결과 검증
```

로그인 자체를 검증하는 테스트는 별도로 두고, 다른 기능에서는 `storageState`로 인증 상태를 재사용한다. 인증 파일에는 민감한 정보가 들어갈 수 있으므로 Git에서 제외한다. 비로그인 상태를 검증하는 테스트에는 인증 상태를 적용하지 않는다.

데이터 준비는 API나 Fixture로 처리하되, 검증하려는 사용자 행동까지 API 호출로 대체하지는 않는다. 게시글 작성 테스트라면 작성은 UI로 수행해야 하고, 수정 테스트라면 수정 동작이 UI 검증 대상이다.

## 다른 테스트의 결과에 의존하지 않기

작성 테스트가 만든 게시글을 수정 테스트가 사용하고, 수정 테스트가 끝난 뒤 삭제 테스트를 실행하는 구조는 피하기로 했다. 각 테스트는 단독 실행과 순서 변경에도 동작해야 한다.

- 필요한 데이터는 해당 테스트에서 준비한다.
- 고정된 데이터 ID 대신 생성 응답에서 받은 ID를 사용한다.
- 병렬 실행에서 충돌하지 않도록 데이터와 필요 시 계정을 분리한다.
- 실패하더라도 테스트 데이터가 남지 않도록 정리 과정을 둔다.

BrowserContext의 격리와 서버 데이터의 격리는 별개이다. 브라우저 환경이 분리되어 있어도 같은 계정의 서버 데이터를 동시에 바꾸면 충돌할 수 있으므로 두 범위를 함께 관리해야 한다.

# 화면 변경과 실행 속도에 흔들리지 않는 테스트

테스트가 사용자 기능의 문제를 알려주는 것이 아니라 CSS 변경이나 실행 환경 차이 때문에 계속 실패한다면 결과를 신뢰하기 어려워진다. 그래서 요소를 찾는 기준과 기다리는 방식을 통일하기로 했다.

## Locator는 사용자가 인식하는 정보를 우선하기

버튼과 링크는 `getByRole()`, 입력 요소는 `getByLabel()`을 우선 사용한다. 화면 텍스트로 구분할 수 있다면 `getByText()`를 사용하고, 적절한 기준이 없다면 `getByTestId()`로 명시적인 테스트 식별자를 둔다.

```ts
page.getByRole('button', { name: '저장', exact: true });
page.getByLabel('이메일');
page.getByRole('dialog', { name: '회원 탈퇴' });
```

복잡한 DOM 경로나 스타일용 클래스에 의존하는 선택자는 가능한 한 피한다. 요소가 여러 개라고 무조건 첫 번째 것을 선택하기보다, 영역과 이름을 구체화해 테스트 의도를 드러낸다. label이나 역할로 요소를 찾기 어렵다면 화면의 접근성 구조도 함께 살펴보기로 했다.

## 고정 시간 대신 필요한 상태 기다리기

`waitForTimeout()`으로 몇 초를 기다리는 방식은 테스트의 통과 기준으로 사용하지 않기로 했다. 실행 환경이 느리면 기다린 시간이 부족할 수 있고, 빠르면 불필요하게 시간을 낭비하기 때문이다.

```ts
await page.getByRole('button', { name: '검색', exact: true }).click();

await expect(page.getByText('검색 결과 10건', { exact: true })).toBeVisible();
```

이 예시는 검색 결과가 10건인 데이터가 준비되어 있다는 전제이다. 임의의 시간이 흘렀는지가 아니라 기대한 상태에 도달했는지를 확인한다. 클릭 전에는 Auto-waiting을 활용하고, 클릭 이후의 결과는 Web-first Assertion으로 기다린다.

# 정상 흐름, 예외 상황과 Mock의 범위

정상 입력으로 성공하는 경우만 테스트하면 실패 상황에서 사용자가 어떤 안내를 받는지 놓칠 수 있다. 중요한 기능은 정상 동작, 사용자 입력 오류, 권한 문제, 시스템 오류를 함께 검토하기로 했다.

| 상황 | 로그인 기능의 예시 | 확인할 결과 |
| --- | --- | --- |
| 정상 동작 | 올바른 계정 입력 | 로그인 상태와 메인 화면 |
| 사용자 입력 오류 | 잘못된 비밀번호 입력 | 오류 안내와 재입력 가능 여부 |
| 권한 문제 | 비로그인 상태로 보호된 경로 접근 | 접근 제한과 로그인 안내 |
| 시스템 오류 | 로그인 API에서 오류 발생 | 실패 안내와 재시도 가능 여부 |

모든 입력 조합을 E2E로 작성하지는 않는다. 세부 입력 규칙은 작은 범위의 테스트로 검증하고, E2E에는 사용자 흐름에 영향을 주는 대표적인 경우를 남긴다. 빈 데이터, 로딩, 없는 데이터 조회 같은 상태도 기능의 특성에 따라 추가한다.

## 실제 서버와 Mock을 나누는 기준

핵심 정상 흐름은 실제 테스트 서버와 통신하도록 구성할 계획이다. 프론트엔드에서 올바른 요청을 보내고, 서버가 처리한 결과를 다시 화면에서 확인하는 연결까지 검증하기 위해서다. 운영 데이터에 영향을 주지 않도록 테스트 환경과 계정을 사용한다.

반면 500 응답, 네트워크 실패, 요청 제한처럼 재현하기 어려운 상황은 Mock으로 만든다. 이때는 정해진 응답에 대한 화면의 대응을 검증하는 것이며, 실제 서버의 처리까지 확인한 것으로 판단하지 않는다.

특히 권한 오류를 Mock으로 반환해 안내 화면이 나오는지 확인하는 것과, 실제 서버가 권한 없는 요청을 거부하는지는 다른 검증이다. 화면에서 버튼을 숨기는 것만으로 권한 검증을 끝내지 않기로 했다.

# 테스트 구조와 CI 운영 기준

## 반복이 생길 때 공통화하기

처음부터 모든 화면을 Page Object로 만들고 여러 계층으로 나누면, 적은 테스트를 이해하기 위해 오히려 많은 파일을 읽어야 할 수 있다. 그래서 처음에는 기능별로 테스트를 나누고 시나리오를 직접 읽을 수 있게 작성하기로 했다.

같은 동작과 Locator의 반복이 많아지면 Page Object로 분리하고, 공통적인 데이터 준비와 정리는 Fixture로 옮긴다. 공통화 이후에도 테스트 파일에서 사용자의 행동과 기대 결과가 드러나야 한다.

## 실행 범위는 단계적으로 확장하기

초기에는 Chromium에서 핵심 테스트를 안정적으로 실행하는 것을 우선한다. 이후 테스트 수와 지원 브라우저 범위를 고려해 CI 실행 범위를 나누기로 했다.

| 실행 시점 | 적용할 기준 |
| --- | --- |
| PR | Chromium에서 빠른 기본 동작 확인과 핵심 흐름 검증 |
| main 병합 후 | Chromium 전체 회귀 테스트 |
| 정기 실행 또는 배포 전 | 지원 대상인 Firefox, WebKit 등을 포함한 검증 |

분류가 필요해지면 `@smoke`, `@critical`, `@regression` 같은 태그를 사용한다. 주요 지원 브라우저에서만 발생하는 문제를 뒤늦게 발견하지 않도록, 해당 환경의 중요도가 높다면 PR 단계에도 포함한다.

## 실패 원인을 확인할 수 있게 남기기

CI에서 실패했을 때 원인을 확인할 수 있도록 Trace와 실패 시 스크린샷을 남길 계획이다.

```ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  retries: process.env.CI ? 1 : 0,
  use: {
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },
});
```

위 설정에서 Trace는 첫 번째 재시도에 기록되므로, 재시도가 없는 로컬 실행에서는 별도 설정이 필요하다. CI에서는 리포트와 Trace 파일을 실행 결과물로 보관하도록 구성한다.

재시도에서 성공했다고 해서 첫 실패를 무시하지는 않기로 했다. 제품 결함인지, 데이터 충돌인지, 준비 상태를 제대로 기다리지 못한 것인지 확인해야 한다. 핵심 테스트는 CI 필수 검사로 연결해 실패 시 병합을 막는 것을 목표로 하되, 먼저 반복 실행에서도 결과를 신뢰할 수 있는 상태를 만든다.

# 정리

이번에 정한 기준은 테스트를 많이 작성하는 것보다, 실패했을 때 의미 있는 정보를 주는 테스트를 만드는 것이다. 코드 리뷰에서도 이 테스트가 어떤 사용자 목적을 검증하는지, 무엇이 확인되어야 성공인지부터 살펴보기로 했다.

1. 핵심 사용자 흐름과 실패 영향을 기준으로 우선순위를 정한다.
2. 하나의 테스트는 하나의 사용자 목적을 검증한다.
3. 준비 과정은 재사용하되 테스트끼리 결과와 변경 가능한 데이터를 공유하지 않는다.
4. 사용자 기준 Locator와 상태 기반 대기를 사용한다.
5. 정상 흐름과 대표적인 실패 상황을 구분해 검증한다.
6. 실제 서버 연동과 Mock 테스트가 보장하는 범위를 구분한다.
7. 공통화와 CI 실행 범위는 필요에 따라 확장한다.
8. 재시도로 실패를 덮지 않고 원인을 확인한다.

이번에는 앞으로 테스트를 작성하고 검토할 때 적용할 기준을 정리했다. 우선 소수의 핵심 시나리오부터 작성하고, 실제 실행 시간과 실패 원인을 살펴보며 기준을 보완할 계획이다.
