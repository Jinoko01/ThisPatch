# TIL - 2026-08-26 (수)

## 오늘 한 것

화요일에 진행한 Steam Review API POC와 수요일에 진행한 장기 호출·패치·메타데이터 검증 내용을 합쳐 정리했다.

### 1. Steam Review API POC

Steam Review endpoint를 직접 호출해 리뷰 데이터 구조를 확인했다.

Counter-Strike 2(appid 730)를 기준으로 `query_summary`를 확인했을 때 약 980만 건 규모의 리뷰가 존재하는 것을 확인했다.

리뷰에서 다음과 같은 필드를 확인했다.

- `recommendationid`, `review`, `language`
- `timestamp_created`, `timestamp_updated`
- `voted_up`, `votes_up`, `weighted_vote_score`
- `playtime_forever`, `playtime_at_review`, `last_played`
- `refunded`, `steam_purchase`, `received_for_free`

특히 `playtime_at_review`와 `refunded`를 활용하면 단순 긍부정 분석을 넘어 플레이타임 구간별 VOC나 환불 리뷰 분석으로 확장할 수 있다고 판단했다.

Steam Review API는 cursor 기반 pagination을 사용하며, 페이지당 100건을 요청할 수 있었다. cursor를 변경하면서 다음 페이지의 리뷰를 가져왔고, 테스트 범위에서는 페이지마다 서로 다른 `recommendationid`가 확인되어 연속 수집 가능성을 검증했다.

### 2. Review Pagination 장기 호출

약 100페이지까지 반복 호출하며 각 페이지의 `recommendationid`를 확인했다. 테스트 과정에서 페이지마다 새로운 ID가 추가되는 것을 확인했고, 테스트 범위에서는 중복 없이 수집되는 것을 관찰했다.

대략적인 측정 결과는 다음과 같다.

- 평균 응답 시간: 약 613ms
- p95: 약 846ms
- 최대 응답 시간: 약 7.5초
- 100페이지 테스트 동안 명시적인 Rate Limit은 발생하지 않음

이를 통해 Review 데이터를 대규모로 Backfill할 수 있는 가능성은 확인했지만, 실제 수백만 건 전체 수집 시에는 API 제한, 실패 요청 재시도, cursor 저장, 중단 후 이어받기, 리뷰 수정, 중복 제거를 고려해야 한다고 정리했다.

### 3. Patch Note / News POC

Steam News API(`ISteamNews GetNewsForApp v2`)에서 `newsitems`와 `tags`를 확인했다. 실제 패치 공지에 `patchnotes` 태그가 포함되는 사례와 패치 본문의 `contents`에 변경사항이 들어오는 것을 확인했다.

패치 내용을 이후 다음과 같은 Change Unit으로 구조화할 수 있다고 정리했다.

```text
Domain
Component
Action
Property
```

### 4. SteamSpy Tag / Metadata POC

SteamSpy에서 게임별 Tag와 Tag Vote Count를 확인했다. Counter-Strike 2와 같은 게임에서 FPS, Shooter, Multiplayer, Competitive 등의 태그와 투표 수를 가져올 수 있었다.

이 데이터는 유사 게임 검색, 장르·태그별 Benchmark, 유사 패치 검색 시 Game Similarity 보조 정보로 활용할 수 있다고 판단했다.

### 5. 프로젝트 방향 구체화

POC 결과를 바탕으로 프로젝트 핵심을 다음처럼 정리했다.

```text
Patch / Update
      ↓
Review / Community Reaction
      ↓
CCU
      ↓
Historical Similar Case
```

단순 Steam 통계 조회를 넘어서 게임의 변경사항과 사용자 반응을 시간축으로 연결하는 방식을 검토했다.

## 배운 것

- 프로젝트 아이디어는 API 문서만 보는 것보다 실제 호출을 통해 필요한 필드와 수집 방식을 검증해야 한다.
- POC의 목적은 데이터를 한 번 받아보는 것이 아니라 이후 파이프라인의 위험요소를 찾는 것이다.
- Review처럼 과거 데이터를 API로 가져오는 데이터와 CCU처럼 지속적으로 쌓아야 하는 데이터는 수집 전략을 구분해야 한다.
- 대규모 수집에서는 병렬화뿐 아니라 재시도, 체크포인트, 중복 제거가 중요하다.

## 느낀 점

Review의 수백만 건 규모와 Patch·Tag 데이터를 직접 확인하면서 Steam 프로젝트의 구현 가능성이 더 명확해졌다. 특히 Review Text, 플레이타임, 환불 여부를 함께 사용하면 사용자 집단별 반응을 다양하게 비교할 수 있다는 점이 흥미로웠다.
