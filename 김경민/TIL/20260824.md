# TIL 2026-08-24 (월)

## 사전학습 — Hadoop과 MapReduce 기초

### Hadoop의 구성

- Hadoop은 대용량 데이터를 여러 컴퓨터에 나누어 저장하고 처리하기 위한 분산 처리 생태계다.
- **HDFS**는 데이터를 여러 노드에 분산 저장하고, **MapReduce**는 여러 머신에서 계산을 나누어 수행한다.
- 하나의 큰 파일은 HDFS에서 블록으로 나뉘며 여러 DataNode에 저장된다.

### NameNode와 DataNode

- **NameNode**는 파일 이름, 디렉터리 구조, 파일을 구성하는 블록의 위치 같은 메타데이터를 관리한다.
- **DataNode**는 실제 데이터 블록을 디스크에 저장하고 클라이언트의 읽기·쓰기 요청을 처리한다.
- 클라이언트가 파일을 읽을 때는 NameNode에서 블록 위치를 확인한 뒤 실제 데이터는 DataNode에서 직접 받는다.

### MapReduce의 처리 흐름

1. **Map**: 입력 데이터를 레코드 단위로 읽고 `(Key, Value)` 중간 결과를 만든다.
2. **Shuffle/Sort**: 같은 Key를 가진 결과를 같은 Reducer로 네트워크 전송하고 묶는다.
3. **Reduce**: 같은 Key의 Value 목록을 집계하여 최종 결과를 출력한다.

- Mapper와 Reducer는 서로 다른 머신에서 실행될 수 있다.
- 가능하면 데이터가 저장된 노드 가까이에서 Mapper를 실행하는 **데이터 지역성**을 활용하여 네트워크 전송을 줄인다.
- **Combiner**는 Mapper가 만든 결과를 로컬에서 미리 집계하여 Shuffle 데이터 크기를 줄이는 선택적 최적화다.

### 입력 Key와 출력 Key의 차이

- 텍스트 입력에서 Mapper가 받는 입력 Key는 보통 행 번호가 아니라 해당 행이 시작되는 **바이트 오프셋**이다.
- 입력 Value는 그 행의 전체 문자열이다.
- WordCount Mapper가 출력하는 `(단어, 1)`에서 단어가 Key가 되는 것은 사용자가 Map 로직에서 새롭게 정한 출력 형식이다.

### 실습 환경 구성

- Windows에 VMware Workstation Pro를 설치하고 Ubuntu 24.04 가상머신을 구성했다.
- 가상머신에 Java 8과 Hadoop 3.2.2를 설치하고 실습용 저장소를 clone했다.
- `jps`로 `NameNode`, `DataNode`, `SecondaryNameNode` 프로세스가 실행되는지 확인했다.

### 핵심 정리

> NameNode는 데이터의 위치를 알려주고, DataNode는 실제 데이터를 저장하며, MapReduce는 데이터 가까이에서 계산한 뒤 Shuffle로 같은 Key를 모아 집계한다.

### 1. 컴퓨트보다 네트워크가 병목이다

노트북 스펙을 실측했다.

| 항목 | 값 |
|---|---|
| CPU | Core Ultra 9 185H (16코어 / 22스레드) |
| RAM | 63.5GB |
| 디스크 여유 | 1.6TB |
| **네트워크** | **Wi-Fi 72.2Mbps ≈ 9MB/s** |

6대를 합치면 96코어 / 384GB / 9.6TB인데 네트워크만 초당 9MB다. 셔플 1TB 소요 시간을 계산해봤다.

| 네트워크 | 1TB 셔플 |
|---|---|
| 현재 Wi-Fi | **약 31시간** |
| 기가비트 유선 | 약 2.5시간 |
| 2.5GbE 유선 | 약 1시간 |

로컬 NVMe가 네트워크보다 약 2000배 빠른 상태다. 이 구성에서는 96코어가 대부분 네트워크 대기에 소모된다.

또한 Wi-Fi는 **반이중 + 공유 매체**라서 6대가 동시에 셔플하면 대역폭을 나눠 쓰는 것이 아니라 AP 하나의 무선 전송 시간을 서로 경합한다. 유선처럼 노드 수에 비례해 총 대역폭이 늘지 않는다.

**결론**: 유선 스위치가 이 프로젝트에서 투자 대비 효과가 가장 큰 항목이다. 2.5GbE 스위치 + USB-C 어댑터 6개(약 20만원)로 셔플 성능 약 30배 개선이 가능하다.

### 2. HDFS 마스터를 클라우드에 두면 안 된다

EC2를 NameNode로 쓰는 구성을 검토하다 구조적 제약을 확인했다.

**HDFS는 NameNode가 블록 위치만 알려주고, 실제 데이터 전송은 클라이언트가 DataNode에 직접 접속해서 수행한다.**

```
DataNode(노트북 6대) = 사내망 NAT 뒤
NameNode(EC2)       = 외부

NameNode: "블록은 DataNode X의 IP:포트에 있습니다"
클라이언트: (NAT 뒤 DataNode에 접근 불가)
```

DataNode·NodeManager는 heartbeat를 외부로 보내므로 **노드 등록은 성공하고 웹 UI에도 정상 표시된다.** 그러나 실제 read/write만 전부 타임아웃된다. 원인 파악이 어려운 유형의 문제다.

**결론**: 마스터 데몬은 LAN 내부 노트북에 배치하고, EC2는 데이터 경로 밖(수집 게이트웨이·서빙)에 둔다.

### 3. AWS 데이터 전송 비용의 방향성

- EC2 → 노트북 = **outbound, 과금** (1TB당 약 10만원)
- 노트북 → EC2 = **inbound, 무료**

이에 따라 데이터 흐름 규칙을 정했다.

| 데이터 | 경로 |
|---|---|
| TB급 대용량 | 노트북이 원본에서 직접 다운로드 (AWS 경유 없음) |
| 분석 결과(MB급) | 노트북 → EC2 업로드 |

### 4. NameNode 메모리는 용량이 아니라 블록 개수에 비례한다

10TB를 128MB 블록으로 분할하면 약 8만 블록이며, 힙 1~2GB로 충분하다. 마스터 노드에 고성능 장비가 필요하지 않다는 의미다.

### 5. ADS-B 항적 데이터 접근성 검증

항공 데이터를 후보로 조사하면서 접근 조건을 확인했다.

**OpenSky Network**는 가장 널리 알려진 소스지만, 문서에 "전량 벌크 다운로드는 일반적인 학생 작업 용도가 아니며 추출 수수료가 부과될 수 있다"고 명시되어 있다. Zenodo 공개 데이터셋은 5.2GB 규모의 항공편 요약 목록으로 궤적 데이터가 아니었다.

**adsb.lol**은 접근 조건이 더 적합했다. GitHub Releases 배포, 신청·인증 불필요, ODbL/CC0 라이선스.

하루치를 실제로 받아 측정했다.

| 항목 | 실측값 |
|---|---|
| 하루 릴리스 | 약 3.0~3.2GB (압축) |
| 파일 개수 | 약 3만 개 (항공기 1대당 1개) |
| **압축률** | **약 4.8배** (100개 샘플) |
| 파일 크기 중앙값 | **918바이트** (최소 170바이트) |
| 1년치 압축 해제 시 | 약 5.5TB |

사전 추정은 5~10배였으나 실측은 4.8배였다. 계획 수립 시 추정값이 아니라 실측값을 써야 한다.

### 6. Small file problem

파일 3만 개에 크기 중앙값 918바이트. 이는 HDFS의 대표적 취약점에 해당한다.

- NameNode 메모리가 파일 개수에 비례하여 증가
- Spark 태스크가 파일 개수만큼 생성되어 오버헤드 발생

tar 구조에서도 동일한 문제가 나타났다. 파일 3만 개 × (512바이트 헤더 + 블록 패딩)으로 인해 **선언된 내용 75MB가 tar 상에서 101MB**가 됐다. 순수 패딩 오버헤드가 약 26MB다.

**대응**: 압축 해제 시 Parquet으로 병합하는 compaction 단계가 필수다. 이는 인위적으로 설정한 기술 과제가 아니라 데이터 구조가 요구하는 작업이다.
