# Playwright와 E2E 테스트

## Playwright란

Playwright는 브라우저를 코드로 조작해 실제 사용자의 행동을 자동화하는 도구이다. Chromium, Firefox, WebKit에서 페이지 이동, 입력, 클릭 등을 수행하고 그 결과를 검증할 수 있다. Playwright Test는 이러한 기능에 테스트 실행, 검증, Fixture, 리포트 등을 제공하는 테스트 프레임워크이다.

E2E(End-to-End) 테스트는 사용자의 관점에서 서비스의 전체 흐름이 정상적으로 동작하는지 확인하는 테스트이다. 개별 함수의 반환값을 확인하는 단위 테스트와 달리, 브라우저에서 여러 기능이 연결된 결과를 검증한다.

```text
로그인 화면 접속
  → 이메일과 비밀번호 입력
  → 로그인 버튼 클릭
  → 인증 처리
  → 로그인 후 화면 확인
```

```ts
import { test, expect } from '@playwright/test';

test('로그인할 수 있다', async ({ page }) => {
  await page.goto('/login');

  await page.getByLabel('이메일').fill('test@example.com');
  await page.getByLabel('비밀번호').fill('test-password');
  await page.getByRole('button', { name: '로그인', exact: true }).click();

  await expect(page).toHaveURL('/home');
});
```

위 예시는 테스트용 계정과 화면이 준비되어 있고, 설정 파일에 `baseURL`이 지정되어 있다고 가정한다. `test`는 시나리오를 정의하고, `page`는 브라우저 탭을 나타낸다. 요소를 찾은 뒤 행동을 수행하고, `expect`로 결과를 검증하는 것이 기본 구조이다.

E2E 테스트는 실제 사용자 흐름을 확인하는 데 유용하지만 실행 비용이 크고 외부 환경의 영향을 받는다. 모든 경우를 E2E로 확인하기보다 로그인, 게시글 작성처럼 중요한 흐름을 중심으로 작성하고, 세부 로직은 단위 테스트와 통합 테스트로 검증하는 것이 좋다.

# Browser, BrowserContext, Page와 테스트 격리

Playwright의 브라우저 환경은 다음과 같은 구조로 구성된다.

```text
Browser
  ├── BrowserContext A
  │     ├── Page A-1
  │     └── Page A-2
  └── BrowserContext B
        └── Page B-1
```

- `Browser`: Chromium, Firefox, WebKit 등의 브라우저 인스턴스이다.
- `BrowserContext`: 쿠키와 저장소 등이 다른 Context와 분리된 독립적인 브라우저 환경이다.
- `Page`: Context 안에서 열린 하나의 탭 또는 팝업이다.

같은 Context의 페이지들은 쿠키를 공유하고, 같은 출처라면 `localStorage`도 공유한다. 반면 `sessionStorage`는 같은 Context 안에서도 탭별로 분리된다. 여러 탭이 같은 사용자로 동작하는 상황은 하나의 Context에서 여러 Page를 열어 테스트할 수 있다.

## Test Isolation

Playwright Test의 기본 `page`, `context` Fixture를 사용하면 테스트마다 새로운 BrowserContext가 제공된다. 따라서 앞선 테스트에서 로그인하거나 저장소에 값을 기록해도 다음 테스트로 그대로 이어지지 않는다.

```text
테스트 A → Context A → A의 쿠키와 저장소
테스트 B → Context B → B의 쿠키와 저장소
```

테스트 격리의 목적은 실행 순서와 다른 테스트의 성공 여부에 의존하지 않도록 만드는 것이다. 예를 들어 게시글 수정 테스트가 게시글 작성 테스트에서 만든 데이터를 사용한다면, 작성 테스트가 실패하거나 수정 테스트만 실행했을 때 문제가 발생한다. 각 테스트는 자신에게 필요한 데이터를 직접 준비해야 한다.

다만 BrowserContext가 분리되어도 서버의 데이터베이스까지 자동으로 분리되지는 않는다. 같은 계정이나 게시글을 여러 테스트에서 동시에 변경하면 충돌할 수 있으므로 테스트별 데이터 생성과 정리, 계정 분리 등을 함께 고려해야 한다.

# Locator와 Action

Locator는 화면에서 조작하거나 검증할 요소를 찾는 방법을 표현하는 객체이다. 한 번 찾은 DOM 요소를 계속 보관하는 방식이 아니라, 실제 동작 시점에 조건에 맞는 요소를 다시 찾으므로 화면이 다시 렌더링되는 상황에도 대응할 수 있다.

| Locator | 요소를 찾는 기준 |
| --- | --- |
| `getByRole()` | 버튼, 링크 등의 역할과 접근 가능한 이름 |
| `getByLabel()` | 입력 요소에 연결된 label |
| `getByText()` | 화면에 표시되는 텍스트 |
| `getByPlaceholder()` | 입력 요소의 placeholder |
| `getByTestId()` | 기본적으로 `data-testid` 속성 |

```ts
const loginButton = page.getByRole('button', {
  name: '로그인',
  exact: true,
});

await page.getByLabel('이메일').fill('test@example.com');
await loginButton.click();
```

CSS 클래스나 복잡한 DOM 경로보다 사용자가 인식하는 역할과 이름을 기준으로 요소를 찾는 것이 좋다. 버튼의 클래스가 변경되더라도 역할과 이름이 유지된다면 테스트를 수정할 필요가 줄어든다. 사용자에게 보이는 정보만으로 요소를 안정적으로 구분하기 어렵다면 `getByTestId()`를 사용할 수 있다.

클릭처럼 하나의 요소를 대상으로 하는 동작에서 Locator가 여러 요소와 일치하면 오류가 발생한다. 무조건 `first()`로 첫 번째 요소를 선택하기보다 영역을 제한하거나 이름을 구체적으로 지정해 의도한 요소를 찾는 것이 좋다.

요소를 찾은 뒤에는 Action으로 사용자 행동을 수행한다.

- `click()`: 클릭한다.
- `fill()`: 입력값을 채운다.
- `check()`, `uncheck()`: 체크박스의 선택 상태를 변경한다.
- `selectOption()`: `<select>` 요소의 항목을 선택한다.
- `press()`: 키보드 키를 입력한다.
- `hover()`: 요소 위로 마우스를 이동한다.

```text
Page → Locator로 요소 지정 → Action 수행 → 결과 검증
```

# Auto-waiting과 Web-first Assertion

## Auto-waiting

Playwright는 Action을 수행하기 전에 해당 요소가 동작 가능한 상태인지 확인한다. 예를 들어 `click()`은 대상이 하나로 결정되는지, 화면에 보이는지, 위치가 안정적인지, 클릭 이벤트를 받을 수 있는지, 활성화되어 있는지 등을 확인한다.

이러한 조건이 충족될 때까지 제한 시간 안에서 기다리는 기능이 Auto-waiting이다. 동작마다 확인하는 조건은 다르며, 제한 시간 안에 필요한 조건을 충족하지 못하면 실패한다.

```ts
// 일정 시간이 지나도 버튼이 준비되지 않을 수 있다.
await page.waitForTimeout(3000);
await page.getByRole('button', { name: '저장', exact: true }).click();

// 클릭에 필요한 상태가 될 때까지 자동으로 기다린다.
await page.getByRole('button', { name: '저장', exact: true }).click();
```

고정 시간 대기는 빠른 환경에서는 불필요한 시간을 소비하고, 느린 환경에서는 시간이 부족해 실패할 수 있다. 따라서 일정 시간 동안 멈추기보다 필요한 상태를 기다리는 방식으로 작성해야 한다.

## Web-first Assertion

Assertion은 행동 이후의 결과가 기대한 상태인지 확인하는 것이다. Playwright의 Web-first Assertion은 조건이 즉시 만족되지 않더라도 제한 시간 동안 반복해서 확인한다.

```ts
await page.getByRole('button', { name: '저장', exact: true }).click();

await expect(page.getByText('저장되었습니다.', { exact: true })).toBeVisible();
```

Auto-waiting이 행동을 수행하기 위한 조건을 기다린다면, Web-first Assertion은 행동 이후 기대한 결과를 기다린다. 버튼을 클릭할 수 있다는 사실이 서버의 저장 처리까지 완료되었다는 의미는 아니므로 두 역할을 구분해야 한다.

```ts
await expect(locator).toBeVisible();
await expect(locator).toBeHidden();
await expect(locator).toHaveText('완료');
await expect(locator).toHaveValue('입력값');
await expect(page).toHaveURL('/home');
await expect(page).toHaveTitle('Home');
```

모든 `expect`가 자동으로 재시도하는 것은 아니다. `expect(await locator.isVisible()).toBe(true)`는 한 번 조회한 불리언 값을 검증한다. 비동기적으로 변하는 화면 상태는 `await expect(locator).toBeVisible()`처럼 Locator를 직접 검증해야 한다.

# Hook과 Fixture

테스트가 많아지면 관련 시나리오를 묶고 공통 준비 과정을 정리해야 한다. `test.describe()`로 테스트를 그룹화하고 Hook으로 실행 전후의 작업을 정의할 수 있다.

```ts
test.describe('로그인', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/login');
  });

  test('잘못된 비밀번호를 입력하면 오류를 보여준다', async ({ page }) => {
    await page.getByLabel('이메일').fill('test@example.com');
    await page.getByLabel('비밀번호').fill('wrong-password');
    await page.getByRole('button', { name: '로그인', exact: true }).click();

    await expect(page.getByRole('alert')).toHaveText('로그인 정보를 확인해주세요.');
  });
});
```

- `beforeEach`, `afterEach`: 각각의 테스트 전후에 실행한다.
- `beforeAll`, `afterAll`: 해당 파일이나 그룹을 실행하는 워커 프로세스에서 전체 테스트 전후에 실행한다.

`beforeAll`을 전체 테스트 실행에서 무조건 한 번만 실행되는 함수로 생각하면 안 된다. 워커가 여러 개이거나 실패 후 워커가 다시 시작되면 여러 번 실행될 수 있다. 또한 테스트마다 생성되는 `page`, `context` Fixture는 `beforeAll`에서 사용할 수 없다.

## Fixture란

Fixture는 테스트에 필요한 자원이나 환경을 준비하고, 테스트가 끝나면 정리하는 구조이다. 테스트 함수의 `async ({ page }) => {}`에서 `page`는 직접 생성한 변수가 아니라 Playwright가 주입한 기본 Fixture이다.

| Fixture | 역할 |
| --- | --- |
| `browser` | 워커에서 공유하는 브라우저 인스턴스 |
| `context` | 테스트별로 격리된 브라우저 환경 |
| `page` | 해당 테스트의 브라우저 탭 |
| `request` | HTTP 요청을 직접 보내는 APIRequestContext |

Hook은 특정 시점에 실행할 작업을 정의하고, Fixture는 테스트에 필요한 자원과 그 생명주기를 관리한다. 처음에는 기본 Fixture를 활용하고, 반복되는 준비와 정리 로직이 많아졌을 때 Custom Fixture로 분리하는 것이 좋다.

# Authentication과 storageState

게시글 작성이나 회원 정보 수정처럼 로그인이 전제인 기능을 테스트할 때 매번 UI로 로그인하면 시간이 오래 걸리고 로그인 화면의 변경에도 영향을 받는다. 이때 인증 상태를 저장하고 재사용할 수 있다.

```text
인증 준비용 setup project
  → 테스트 계정 로그인
  → 로그인 완료 확인
  → storageState 파일 저장
  → 의존하는 테스트들이 저장된 상태로 시작
```

```ts
// 인증 준비 단계에서 로그인 완료를 확인한 뒤 저장한다.
await page.context().storageState({ path: 'playwright/.auth/user.json' });
```

```ts
// 저장된 인증 상태를 사용할 테스트 파일에 설정한다.
test.use({ storageState: 'playwright/.auth/user.json' });

test('게시글 작성 화면에 접근할 수 있다', async ({ page }) => {
  await page.goto('/posts/new');
  await expect(page.getByRole('heading', { name: '게시글 작성' })).toBeVisible();
});
```

인증 파일은 테스트 실행 전에 생성되어 있어야 하며, setup project와 프로젝트 의존성으로 순서를 보장할 수 있다. 같은 파일을 사용하더라도 테스트들은 각자의 Context에 상태를 불러오므로 브라우저 환경의 격리는 유지된다.

`storageState`는 쿠키와 `localStorage`를 저장한다. 인증이 IndexedDB에 의존한다면 저장 시 `indexedDB: true` 옵션이 필요하며, `sessionStorage`는 기본 저장 대상이 아니므로 별도 처리가 필요하다.

인증 파일에는 계정을 대신 사용할 수 있는 민감한 정보가 포함될 수 있으므로 Git에 커밋하지 않아야 한다. 또한 같은 계정의 서버 데이터를 동시에 변경하는 테스트는 충돌할 수 있다. 로그인 기능 자체를 검증할 때는 저장된 인증 상태를 사용하지 않고 실제 로그인 과정을 테스트해야 한다.

# APIRequestContext와 Network Mocking

## API로 테스트 데이터 준비

Playwright는 `APIRequestContext`를 통해 브라우저 조작 없이 HTTP 요청을 보낼 수 있다. 이를 이용하면 검증 대상이 아닌 준비 과정을 간단하게 만들 수 있다.

예를 들어 게시글 수정 테스트는 게시글 작성 UI부터 반복할 필요가 없다. API로 게시글을 생성한 뒤 수정 기능을 UI로 검증하면 테스트의 목적이 명확해진다.

```ts
const response = await request.post('/api/posts', {
  data: { title: '수정 테스트용 게시글' },
});

expect(response.ok()).toBeTruthy();
const post = await response.json();

await page.goto(`/posts/${post.id}/edit`);
await page.getByLabel('제목').fill('수정된 제목');
await page.getByRole('button', { name: '저장', exact: true }).click();

await expect(page.getByRole('heading', { name: '수정된 제목' })).toBeVisible();
```

위 코드는 `page`와 `request` Fixture를 받는 테스트 본문 예시이며, API가 생성한 게시글의 `id`를 반환한다고 가정한다. 게시글 ID를 고정하지 않고 응답값을 사용하며, 테스트가 실패하더라도 생성한 데이터가 정리되도록 Fixture나 `try/finally` 등을 구성해야 한다.

기본 `request` Fixture가 브라우저에서 이후에 변경된 쿠키를 자동으로 공유하는 것은 아니다. 브라우저 Context의 쿠키를 함께 사용해야 한다면 `page.request` 또는 `context.request`를 사용할 수 있다.

## Network Mocking

Network Mocking은 브라우저의 요청을 가로채 원하는 응답을 반환하는 방식이다. 실제 서버에서 재현하기 어려운 오류나 빈 응답을 만들어 화면의 대응을 검증할 수 있다.

```ts
test('게시글 조회 실패 시 오류 안내를 보여준다', async ({ page }) => {
  await page.route('**/api/posts', async (route) => {
    await route.fulfill({
      status: 500,
      json: { message: 'Internal Server Error' },
    });
  });

  await page.goto('/posts');

  await expect(page.getByText('잠시 후 다시 시도해주세요.')).toBeVisible();
});
```

요청이 발생한 뒤에는 가로챌 수 없으므로 `page.route()`는 페이지 이동이나 클릭보다 먼저 등록해야 한다. 또한 Mock 테스트는 정해진 응답에 대한 프론트엔드 동작을 검증하는 것이므로 실제 백엔드와의 연동까지 보장하지는 않는다. 실제 서버를 사용하는 주요 흐름 테스트와 역할을 나누어야 한다.

# Projects, CI와 Trace Viewer

Projects는 같은 테스트를 서로 다른 설정으로 실행하기 위한 단위이다. 브라우저 종류뿐 아니라 모바일 화면 크기, 인증 상태, 접속 환경 등을 구분할 수 있다.

```ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  retries: process.env.CI ? 1 : 0,
  use: {
    baseURL: 'http://localhost:5173',
    trace: 'on-first-retry',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
  ],
});
```

이 설정은 테스트 대상 서버가 실행 중이라고 가정한다. CI에서는 의존성과 브라우저 설치, 서버 실행, 테스트 데이터 준비를 거친 뒤 테스트를 실행하고, 실패 분석에 필요한 리포트와 Trace 파일을 보관해야 한다.

Trace Viewer는 테스트에서 수행한 Action, DOM 스냅샷, 네트워크 요청, 콘솔 메시지 등을 시간순으로 확인하는 도구이다. 로컬에서는 성공하지만 CI에서 실패하는 경우 당시 상태를 확인하는 데 도움이 된다.

```bash
npx playwright test
npx playwright show-trace path/to/trace.zip
```

`trace: 'on-first-retry'`는 첫 번째 재시도에서 Trace를 기록하므로 재시도가 설정되어 있어야 한다. 위 설정은 CI에서 한 번 재시도하지만 로컬에서는 재시도하지 않으므로, 로컬 실패를 조사할 때는 Trace 설정을 별도로 조정해야 한다.

재시도는 실패 원인을 해결하는 기능이 아니다. 간헐적으로 성공과 실패를 반복한다면 고정 시간 대기, 테스트 간 데이터 공유, 불안정한 Locator 등을 확인해야 한다. 병렬 실행을 늘리기 전에도 테스트 데이터가 충돌하지 않는지 검토해야 한다.

# Codegen, UI Mode와 학습 정리

Codegen은 브라우저에서 직접 수행한 행동을 테스트 코드로 생성하는 도구이다. 처음 테스트를 작성하거나 Locator를 찾을 때 초안으로 활용할 수 있다.

```bash
npx playwright codegen http://localhost:5173
npx playwright test --ui
```

UI Mode에서는 테스트를 선택해 실행하고 실행 과정과 결과를 확인할 수 있다. Codegen이 생성한 코드는 불필요한 동작을 줄이고, Locator와 결과 검증을 보완한 뒤 사용해야 한다.

## 정리

Playwright를 학습할 때는 API 이름을 외우는 것보다 다음 흐름을 이해하는 것이 중요하다.

```text
Fixture로 격리된 테스트 환경 준비
  → Page에서 화면 이동
  → Locator로 요소 지정
  → Auto-waiting 후 Action 수행
  → Web-first Assertion으로 결과 확인
  → 테스트 데이터와 자원 정리
```

- 사용자가 확인할 수 있는 동작과 결과를 중심으로 테스트한다.
- 테스트는 실행 순서에 의존하지 않도록 필요한 상태를 직접 준비한다.
- 고정 시간 대기보다 행동 가능한 상태와 기대한 결과를 기다린다.
- 인증 재사용과 API 호출로 준비 과정을 줄이되, 검증하려는 동작은 생략하지 않는다.
- Mock 응답을 사용하는 테스트와 실제 서버 연동 테스트의 검증 범위를 구분한다.
- 실패한 테스트는 재시도 횟수만 늘리지 않고 Trace로 원인을 확인한다.

결국 안정적인 E2E 테스트를 작성하려면 브라우저를 조작하는 방법뿐 아니라, 어떤 상태에서 시작해 무엇을 검증하고 어떻게 정리할지까지 함께 설계해야 한다.
