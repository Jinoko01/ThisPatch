## 2026-08-24 | 빅데이터 분산 처리 프로젝트 주제 탐색

프로젝트 주제를 정하기에 앞서, 단순히 데이터의 크기가 큰 주제보다는 **대규모 데이터를 지속적으로 수집·가공해야 하고, 분산 처리를 사용했을 때 명확한 이점이 있는 문제**를 찾는 방향으로 여러 아이디어를 검토했다.

주제를 비교할 때 다음과 같은 기준을 중심으로 살펴봤다.

* 실제 해결하고자 하는 문제가 명확한가
* 충분한 규모의 데이터를 확보할 수 있는가
* 과거 데이터가 누적될수록 분석 가치가 커지는가
* 단순 API 호출이나 기존 검색 서비스로 대체되지는 않는가
* Hadoop / Spark를 사용하는 이유가 자연스러운가
* 6명, 7주 내에 구현 가능한 범위인가
* 결과를 사용자에게 직관적으로 보여줄 수 있는가

### 1. 글로벌 사건 → 공급망 충격 전파

전쟁, 자연재해, 무역 규제 등의 글로벌 사건이 발생했을 때 특정 산업이나 기업의 공급망에 영향이 어떻게 전파되었는지 분석하는 아이디어를 검토했다.

```text
Global Event
     ↓
국가 / 기업 / 산업
     ↓
Supply Chain
     ↓
가격 / 생산 / 물류 변화
```

기업과 산업의 관계를 그래프로 구성하면 대규모 그래프 분석과 시계열 처리를 적용할 수 있다는 점이 흥미로웠다.

**반려 이유**

실제 충격의 전파 과정을 분석하려면 단순히 기업의 1차 공급 관계뿐 아니라 2차, 3차 공급망까지 추적할 필요가 있었다. 하지만 기업 간 다단계 공급망 관계를 충분한 규모로 확보하기 어려워 실제 공급망 구조를 구성하는 데 한계가 있다고 판단했다.

### 2. 농수산물 유통망 분석 및 공급 충격 시뮬레이션

지역별 농수산물 생산량, 도매시장 거래량, 가격 등의 데이터를 이용해 특정 지역의 공급량 변화가 다른 지역의 가격과 유통에 어떤 영향을 미치는지 분석하는 아이디어를 검토했다.

예를 들어 특정 지역의 생산량이 감소했을 때,

```text
생산량 감소
   ↓
도매시장 반입량 변화
   ↓
지역별 가격 변화
```

와 같은 흐름을 분석하는 방식이다.

공공데이터를 활용할 가능성이 높고 시계열 데이터가 지속적으로 쌓인다는 장점이 있었다.

**반려 이유**

생산지와 도매시장에 대한 데이터는 어느 정도 확보할 수 있었지만, 도매시장 이후 상품이 어떤 소매점으로 이동하는지를 연결할 수 있는 데이터가 부족했다. 따라서 생산 → 도매 → 소매로 이어지는 전체 유통망을 구성하기 어렵다고 판단했다.

### 3. 가상 도로·철도 개통에 따른 접근성 변화 시뮬레이션

현재 도로와 철도망을 그래프로 구성하고 새로운 도로나 철도가 추가되었을 때 지역 간 접근성이 어떻게 달라지는지 계산하는 아이디어를 검토했다.

```text
현재 교통망
    +
가상 도로 / 철도
    ↓
최단거리 재계산
    ↓
지역별 접근성 변화
```

전국 단위 도로망을 대상으로 반복적인 그래프 연산을 수행할 경우 분산 그래프 처리를 활용할 수 있다는 점이 흥미로웠다.

**반려 이유**

가상 도로나 철도를 추가했을 때 접근성이 어떻게 변하는지는 계산할 수 있었지만, 그 결과 이후에 서비스를 어떤 방향으로 확장할 수 있을지가 명확하지 않았다. 단발성 시뮬레이션에 가까워질 가능성이 높아 지속적으로 사용할 수 있는 서비스로 발전시키기 어렵다고 판단했다.

### 4. 오픈소스 생태계 위험 / 지속가능성 분석

GitHub의 Repository, Commit, Issue, Pull Request, Contributor, Dependency 데이터를 이용해 오픈소스 프로젝트의 생태계를 분석하는 아이디어를 검토했다.

예를 들어 하나의 프로젝트가 많은 라이브러리에 의존하고 있다면,

```text
Project
 ├─ Library A
 │    └─ Library C
 ├─ Library B
 └─ Library D
```

특정 핵심 라이브러리에 문제가 발생했을 때 여러 프로젝트로 영향을 전파할 수 있다.

다음과 같은 요소를 분석할 수 있다고 생각했다.

* Contributor 수 변화
* Commit 활동 변화
* Issue 처리 속도
* 핵심 Maintainer 의존도
* Dependency 관계
* 특정 Dependency 장애의 영향 범위

GitHub의 대규모 이벤트 데이터와 Dependency Graph를 활용할 수 있어 분산 처리와 연결하기 좋은 주제였다.

**반려 이유**

Commit이나 Release가 오랫동안 없다는 사실만으로 해당 프로젝트가 위험하거나 관리되지 않고 있다고 판단하기 어려웠다. 실제로 방치된 프로젝트일 수도 있지만 이미 기능이 완성되어 추가 개발이 거의 필요하지 않은 프로젝트일 수도 있기 때문이다.

따라서 활동량이나 최근 개발 여부와 같은 데이터만으로 오픈소스의 지속가능성과 위험도를 신뢰성 있게 판단하기 어렵다고 생각했다.

### 5. 논문 / 근거 기반 정보 탐색

논문 본문, Abstract, Citation 관계를 분석하여 사용자의 질문과 관련된 근거를 찾아주는 서비스를 검토했다.

단순 키워드 검색보다

```text
Question
   ↓
관련 논문 검색
   ↓
근거 문장 추출
   ↓
인용 관계 확인
```

과 같이 여러 논문에 흩어진 근거를 연결하는 방향을 생각했다.

논문 데이터 자체의 규모가 크고 텍스트 분석과 Citation Graph를 함께 활용할 수 있다는 장점이 있었다.

**반려 이유**

논문 검색, AI 기반 논문 요약, 질문에 대한 근거 탐색 기능을 제공하는 기존 서비스가 이미 다양하게 존재하고 있었다. 단순히 논문을 검색하고 요약하거나 관련 근거를 찾아주는 기능만으로는 기존 서비스와 명확한 차별점을 만들기 어렵다고 판단했다.

### 6. Steam 리뷰 기반 게임 평가 요소 분석

Steam은 전체·최근 평가를 제공하지만, 사용자가 **왜 게임을 긍정적 또는 부정적으로 평가하는지** 구체적으로 파악하기 어렵다.

이를 보완하기 위해 Steam 리뷰를 NLP로 분석하여 다음과 같은 Aspect와 Sentiment로 정형화하는 아이디어를 검토했다.

* Gameplay
* Performance
* Bug
* Content
* Balance
* Monetization

예를 들어 하나의 리뷰에서 여러 평가 요소를 동시에 추출한다.

```text
"The combat is great, but performance is terrible."

→ Gameplay    : Positive
→ Performance : Negative
```

이렇게 구조화된 데이터를 기반으로 다음과 같은 분석을 생각했다.

* Aspect별 언급률 및 긍·부정 비율
* 출시 초기와 현재 비교
* 최근 기간별 평가 변화
* 패치 전후 평가 변화
* 최근 증가하는 불만 요소

또한 초기 수천만 건 규모의 리뷰 분석, 모델 변경 후 전체 재처리, 대규모 Backfill처럼 반복적으로 많은 데이터를 처리하는 작업에 Spark 기반 Batch Processing을 적용할 수 있다는 점도 검토했다.

단순 감성분석보다 **대규모 비정형 리뷰를 정형화하고 시간에 따른 평가 요소의 변화를 분석할 수 있다는 점**이 흥미로웠다.

**검토 결과**

단순 리뷰 감성분석만 수행한다면 Hadoop이나 Spark를 사용할 필요성이 크지 않을 수 있다는 점을 확인할 필요가 있었다.

반면 대규모 리뷰를 초기 일괄 처리하거나, NLP 모델이 변경될 때 기존 리뷰 전체를 다시 처리하고, 게임·기간·Aspect별 결과를 반복적으로 집계하는 작업까지 고려하면 분산 Batch Processing을 적용할 수 있는 지점이 존재한다고 판단했다.

따라서 실제 Steam 데이터의 규모와 API를 통한 수집 가능성을 먼저 확인한 뒤 프로젝트 적용 가능성을 추가로 검증하기로 했다.

## 주제 탐색을 통해 느낀 점

처음에는 데이터가 크거나 그래프 연산이 가능하면 분산 처리 프로젝트에 적합하다고 생각했지만, 여러 아이디어를 비교하면서 **데이터 규모만으로는 분산 처리의 필요성을 설명하기 어렵다**는 점을 알게 되었다.

실제 프로젝트에서는

```text
대규모 데이터가 존재하는가
        +
반복적인 전처리 / 집계 / 재처리가 필요한가
        +
과거 데이터가 누적될수록 분석 가치가 높아지는가
        +
분석 결과가 실제 서비스 기능으로 연결되는가
```

를 함께 고려할 필요가 있다고 생각했다.

또한 아이디어 자체가 흥미로운 것과 실제 데이터를 확보하여 제한된 기간 안에 구현할 수 있는 것은 별개의 문제이므로, 이후에는 관심 있는 후보들을 대상으로 **실제 데이터 존재 여부와 수집 가능성을 POC를 통해 검증하는 과정**이 필요하다고 판단했다.
